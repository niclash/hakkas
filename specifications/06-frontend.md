# 06 — Frontend

The frontend is the browser editor in which users see and change the running processes. It lives in the repository, in `frontend/`, and is built and versioned together with the engine. It speaks the wire protocol of `02-wire-protocol.md`, is served by the engine's web server (`05-app-lifecycle-persistence.md` §3) and holds no state of its own beyond what the engine's events tell it.

**Status**: this is the second generation of the UI. The first was built on GoJS (commercial); this one is a restart on the open-source **Rete** (v2) editor framework and is far from complete. Features are added step by step, because several design decisions depend on how incomplete versions are actually used. §7 lists what is missing.

**Technology**: Vue 3 with TypeScript, built by Vite; Rete v2 with its area, connection, Vue rendering, context menu, minimap, reroute and auto-arrange plugins; `@noble/hashes` for the login's cryptography (§2). The styles are the frontend's own (§4.1; Bootstrap was dropped with the themes, 2026-10-14). Dependencies are pinned in `frontend/package-lock.json`.

## 1. Building and serving

`npm install && npm run build` in `frontend/` type-checks the sources (`vue-tsc`) and builds the bundle into `frontend/dist` (`index.html` and `assets/`). Neither `node_modules/` nor `dist/` is committed. The engine's CMake build does not build the frontend, so working on the C code needs no Node.js toolchain.

The web server serves `webdir` (`05-app-lifecycle-persistence.md` §1.1). Its default is chosen so that neither case needs an option (decided 2026-10-13):

- **Developing hakkas** (POSIX): the default is the source tree's `frontend/dist`, an absolute path the CMake build compiles in (`HAKKAS_DEFAULT_WEBDIR`). The engine finds the frontend from any working directory: a shell in the repository, CLion's run configurations, a scratch directory for test data.
- **Packaged for users** (POSIX): configuring with `-DHAKKAS_PACKAGE=ON` makes the default `<prefix>/share/hakkas/web` (`CMAKE_INSTALL_FULL_DATADIR`), and `cmake --install` installs the executable and copies `frontend/dist` there (the install fails if the frontend has not been built). A package build never refers to the source tree.
- **Zephyr**: the assets are files on the device's flash (§5), under the default `webdir` of `05-app-lifecycle-persistence.md` §1.3.
- In every case `webdir` in `hakkas.json` and `--webdir` override the default. At startup the web server warns when `webdir` has no `index.html` (nor `index.html.gz`) — usually a frontend that has not been built — instead of answering every request with `404` in silence.

**Development server**: `npm run dev` serves the frontend from Vite, with live reloading, on its own port (5173). The page's port + 1 is then not the engine's WebSocket, so the environment variable `VITE_HAKKAS_WS` gives its URL (e.g. `ws://localhost:8081/`), and the engine must accept the page's origin: `"allowed_origins": ["http://localhost:5173"]` in `hakkas.json` (`02-wire-protocol.md` §0). `npm run build` is run without `VITE_HAKKAS_WS`, so the bundle uses the page's port + 1.

## 2. Connection and login

- **WebSocket URL**: `ws://<page host>:<page port + 1>/` (`wss://` for an `https://` page), as `02-wire-protocol.md` §0 requires; the port of a page without one is the scheme's default (80, 443). An IPv6 host is written in brackets.
- **One connection per login**: logging in opens a new WebSocket; logging out, a session expiry (`environment:logout`), a failed login and a lost connection close it and return to the login screen. A lost connection says so on that screen; there is no automatic reconnection yet.
- **Resuming after a reload** (`02-wire-protocol.md` §2.3.1, implemented in plan task 46): every login reply's `resume` id is kept in the browser's `localStorage` (key `hakkas.session`) with the user name and the resume key — `HMAC(StoredKey, "Resume Key," + nonce)`, computed with the login's proof and never sent; the password is not kept. When the page loads and a session is kept, the frontend resumes it at once (the login form shows "Resuming the session..." meanwhile) and keeps the reply's new id: an id is used once. A resume that fails (the session has expired, the engine restarted, another tab used the id) forgets the kept session and shows the login form **without** an error message: that is the normal end of a session, not a mistake. A logout and a session expiry forget it too. A connection that cannot be made keeps it (the message says the server cannot be reached; the next reload tries again). The kept session is per browser and origin, so tabs share it: a reload of any tab resumes the chain and moves its id on.
- **Login** (`02-wire-protocol.md` §2.3): `environment:challenge` with the user name and a client nonce of 18 random bytes, then `environment:login` with the SCRAM-SHA-256 proof. The key stretching (PBKDF2, 100 000 iterations by default) takes a few hundred milliseconds; the form shows that it is logging in meanwhile. The password is kept only until the proof is computed. The client checks the reply's `server_signature` and refuses a login whose signature does not match ("The server could not prove its identity"), so a device that does not know the user's server key is not trusted. A `network:error` before the login has succeeded (e.g. `"Login failed"`) is shown on the login screen.
- **Cryptography in JavaScript**: `crypto.subtle` exists only in secure contexts, and the device is normally reached as plain `http://<device-ip>` (`02-wire-protocol.md` §2.3, "Browser note"), so the frontend always uses `@noble/hashes` (PBKDF2-HMAC-SHA256, HMAC, SHA-256), audited pure JavaScript, one code path everywhere.
- **Nothing secret in the console**: the frontend logs each message's protocol and command, and its payload except for the `environment` protocol, whose payloads carry the session secret, nonces, proofs and resume ids. An outgoing message's `secret` is never logged.
- After the login the frontend sends `runtime:getruntime`, which brings the block types (`component:component`) and the processes (`network:status`).

## 3. The view follows the engine's events

The frontend obeys `02-wire-protocol.md` §1.1 strictly: **a user action only sends a command; the view changes only when the resulting event arrives**, for the sender as for every other client. A refused command therefore needs no rollback (its `network:error` is shown in a dismissable list, the latest five), and several users editing one process see the same state.

- **The client model** (`frontend/src/components/model.ts`) is fed in one place, attached to each connection before its login: the block types from `component:component` (replacing a type of the same name, so a changed group type updates in place); the processes from `network:status`, `runtime:new_graph`, `runtime:delete_graph`, `network:started`/`stopped` and `graph:rename`; the open process from `graph:clear`. The Vue components only render it.
- **The open process** is selected by `graph:connect`. Its view is cleared by the `graph:clear` that starts the snapshot (`02-wire-protocol.md` §4.1.1) — not when the user clicks — and built from the snapshot and the events after it.
- **Events are applied one at a time, in arrival order**: applying an event to the Rete editor is asynchronous, so each graph event waits for the previous one to finish (a promise chain). Otherwise an `addedge` could be applied before the `addnode`s of its blocks have completed and be lost.
- **Events of other processes** are ignored by the view. Before its first `graph:connect` a connection receives the graph events of every process (`02-wire-protocol.md` §4.1); only the open process's are drawn.
- While an event is being applied the editor's own change hooks are disabled, so drawing an event never sends a command back.

## 4. Rendering a process

- A **block** is a Rete node titled with the block id, its ports taken from its type's `component:component`: outputs first, then inputs, each in the type's port order. A block whose type is not registered (a placeholder, `05-app-lifecycle-persistence.md` §2.2) is drawn without ports.
- A block's **position** is its metadata's `x`/`y`, from `graph:addnode` and `graph:changenode`. Other metadata is not used yet.
- A **connection** is a Rete connection between the two ports.
- An **initial** (a fixed value) is drawn as a **value node** connected to its input (§4.3); the value is shown as the event carries it (a string, `02-wire-protocol.md` §3.4).
- A block added from the palette (§4.5) or the context menu (§4.4) is named after its type with the first number not taken in the process: `math/Add2` → `Add2_1`, `Add2_2`, … The name goes in the `graph:addnode` command; the block appears with its event.
- When the snapshot has arrived, the view zooms to fit the process. The snapshot has no end marker, so this happens after a pause of 150 ms in the events following a `graph:clear`. The editor's element carries `data-settled="true"` once that fit is done (`false` from the `graph:clear` until then): before it, blocks move under the pointer, so the tests (§6) wait for it before they touch the view.

### 4.0 Selecting blocks

Implemented 2026-10-14 (plan task 26). The **selection** is the view's own state, not the engine's: it is not sent, and another client does not see it. What is done *to* the selection goes to the engine as commands, and the view changes only with their events (`02-wire-protocol.md` §1.1).

- **Selecting**: a click on a block selects it alone; Ctrl-click or Shift-click (⌘ on a Mac) adds an unselected block or unselects a selected one. Pressing a selected block keeps the selection, so that dragging it drags all of them; a plain click on it (no movement) then selects it alone.
- **The marquee**: a Shift- or Ctrl-drag on the empty canvas draws a rectangle; the blocks whose middle is inside it are added to the selection. A plain drag on the canvas still pans the view.
- **Clearing**: Escape, or a click on the empty canvas (a press released within a few pointer movements; a drag pans and keeps the selection). **Ctrl+A** (⌘A) selects every block of the process.
- **Delete or Backspace** sends one `graph:removenode` per selected block (the engine removes their connections too); each block leaves the view, and the selection, with its event. With nothing selected the keys do nothing. Keys typed into a field are the field's.
- **Moving the selection**: dragging a selected block moves every selected block by the same amount. No block moves locally; each one's new position goes to the engine as `graph:changenode`, at most one command per block and animation frame (the latest position), and the final positions when the pointer is released. Rete's own node selection (`selectableNodes`) is not used, since it moves the other selected blocks locally.
- A block removed by an event leaves the selection, and opening a process starts with none; a renamed block stays selected.

### 4.2 The inspector

Implemented 2026-10-14 (plan tasks 27–29). A panel to the right of the editor shows the selection (§4.0), and is where a block is renamed and its inputs' fixed values are set; live values come later (plan task 34).

- **Nothing selected**: a hint to select a block.
- **One block**: its id, in a name field (below); its type; the type's description; its inputs, then its outputs, in the type's port order, each with its id, type and description; each input also with what feeds it (below). All of it comes from the type's `component:component`, so it is the engine's own description. A block whose type is not registered (a placeholder, `05-app-lifecycle-persistence.md` §2.2) is said to be one, without ports.
- **Several blocks**: their number and ids.
- **Actions**: Delete, the same as the Delete key (§4.0), for one or several blocks.
- It follows the events: a block renamed by another client shows its new id, and a removed block leaves it.
- **Renaming** (plan task 28): Enter in the name field, or leaving it (also by clicking another block or the canvas), sends `graph:renamenode` when the name changed; the block and the field show the new id when its event arrives. **F2** (one block selected) and **Rename** in a block's context menu select that block and focus the field with its text selected. **Escape** in the field puts the block's id back (and does not clear the selection). Blocks added from the palette keep their `<Type>_<n>` names (§4). The engine alone decides what is valid (no check in the browser).
- **A refused rename** is shown under the field, not with the other errors, and the field is marked invalid until it is edited, left or reverted; leaving it puts the block's id back. The wire's `network:error` names no command (`02-wire-protocol.md` §3.4.1), so while a rename is pending the inspector takes as its refusal only the messages a rename can cause: `"Node exists: <new id>"`, `"Invalid id"`, `"Unknown node: <old id>"` and `"Not permitted: graph:renamenode"` (`src/components/renaming.ts`). A rename sent by clicking another block is no longer shown in the field, so its refusal goes with the other errors.
- **Fixed values on inputs** (initials, `02-wire-protocol.md` §3.4; plan task 29): each input shows what feeds it — **"Connected from `<block>.<port>`"** (no editor: an input has one source, `01-architecture-overview.md` §2.2; remove the connection first), a **fixed value** in an editor, or **"Default: 0"** — the type's resting value, `0`, `false` or empty (there are no per-port defaults, `03-block-types.md` §1) — and an empty editor. The editor fits the port's type: a **switch** for `bool` (a change sends at once), a **text field** for `string`, and a **number field** for `number` and any other type (the engine reads other types like `number`). Enter or leaving the field sends `graph:addinitial` when the value changed, a number as a JSON number and text as it was typed; text that is not wholly a number is not sent ("Enter a number", since the engine would read it as 0). An empty number field, or **×** beside a fixed value, sends `graph:removeinitial`; an empty text field is a value (the empty string). Escape puts the value back. The editor shows the value from the event (a string, as the block's label does, §4). A value being typed when another block is clicked is sent first. As with renaming, the refusals a pending command can cause (`"Input already connected: <block>.<port>"`, `"Unknown node"`, `"Unknown port"`, `"No such connection"`, `"Not permitted: graph:addinitial"`/`removeinitial`; `src/components/initials.ts`) are shown under the input, not with the other errors. An input's context menu sets, changes or clears the value too (§4.4).

### 4.3 Value nodes

Decided with the user 2026-10-14 (plan task 29): a fixed value is drawn like the connection it is — in the graph file a connection whose source is a value, `{"src": {"data": 12}, "tgt": {...}}` (`05-app-lifecycle-persistence.md` §2.1), the sister project's form — as a small **value node** with a dashed line to its input. No protocol change: the value stores no position, so the node is **placed beside its input** (left of the block, level with the input's socket) and follows its block when the block moves; it cannot be dragged on its own (a movable, saved position would need upstream's optional `metadata` on `graph:addinitial`, not taken). Close blocks can make a value node overlap the block to its left.

- **Setting a value**: draw a line from a free input and drop it on the canvas: a box beside the input asks for the value — a field for a number or text (Enter sends `graph:addinitial`; a number is checked as in §4.2), true/false buttons for a bool. Escape, or a click on the canvas, drops the box without sending. The value node appears with the event, which closes the box; a refusal is shown in the box.
- **Changing it**: double-click the value node: a field for a number or text (Enter sends, Escape keeps the value, an empty number field removes it); a bool toggles at once. A refusal is shown under the node.
- **Removing it**: pull its line off the input and drop it on the canvas (`graph:removeinitial`), or **Remove value** in the value node's or its line's context menu (§4.4). Dropped on another input instead, the value **moves** there (`removeinitial`, then `addinitial` with the same value). A line drawn from the value node onto another input copies the value there.
- **A connection drawn onto an input that has a fixed value replaces it**: the editor removes the input's line first (`removeinitial`), then `addedge`, as for an input fed by another connection.
- Value nodes are not blocks: they are not selected (click, marquee, Ctrl+A), not moved by a dragged selection, and have no Rename; a block's removal removes them with its `removeinitial` events. The inspector (§4.2) shows the same values and edits them too.

### 4.4 Context menus

Implemented 2026-10-14 (plan task 30). A right-click in the editor opens the editor's own menu (Rete's classic context menu plugin is no longer used), styled by the theme (§4.1). What it offers depends on what was clicked; every item that changes the process sends commands, and the view changes with their events.

- **The canvas**: *Add block…* (turns the menu into a search over the block types — a type whose name after its family starts with the text first, then any containing it, case ignored; Enter or a click adds the highlighted one **where the menu was opened**, named as from the palette, §4), *Select all* (Ctrl+A), *Zoom to fit*, *Arrange blocks* (the auto-arrange plugin computes a layout without applying it; a `graph:changenode` is sent for each block whose position changes, and the blocks move with the events).
- **A block**: *Rename* (F2, §4.2), *Edit inputs* (selects the block alone and focuses the inspector's first input that takes a value), *Delete* — or *Delete N blocks* when the block is part of a selection of several (§4.0).
- **An input** (a right-click on its row in a block): *Set fixed value…* (the value box of §4.3) when it has neither a connection nor a value; *Change fixed value…* and *Use the default* when it has a value; *Disconnect* (`graph:removeedge`) when it has a connection.
- **A value node or its line** (§4.3): *Change value…* (opens the node's field, or toggles a bool) and *Remove value*.
- **A connection**: *Delete connection* (`graph:removeedge`).
- **Keyboard**: the menu key or Shift+F10 opens the menu of the first selected block, or the canvas's when nothing is selected; the first item is focused, the arrow keys, Home and End move, Enter chooses, Escape closes; keys typed in the menu do not reach the editor. A click outside closes it. A menu that would leave the editor is moved inside it.
- A right-click no longer inserts a reroute pin on a connection: only the main button's presses reach the reroute plugin.
- Items for later tasks join these menus with them: watch a value (plan task 34), expose a port as a process port (35), create a composite from a selection (36), copy, paste and duplicate (37).

### 4.5 The palette and the sockets

Implemented 2026-10-14 (plan task 31).

- **The palette** lists the block types by family (the prefix before `/`), in the order the engine describes them. A **search field** above it keeps only the matching types (the same matching as the context menu's *Add block…*, §4.4) and opens every family with a match; Escape in the field clears it. Each type's **tooltip** gives its full name, its description and its ports with their types (`Inputs: in1 (number), in2 (number)`).
- **Adding a block**: a click on a type adds it in the middle of the editor's view; **dragging** a type onto the editor adds it where it is dropped. Either way the `graph:addnode` carries the position, named as in §4, and the block appears with its event.
- **Sockets by port type**: each port's socket is colored by its type — `number`, `bool` and `string`, the engine's types — from the theme variables `--hk-socket-number`, `--hk-socket-bool` and `--hk-socket-string` (in all three delivered themes; any other type keeps `--hk-socket`). The socket's tooltip is its type, and a **legend** in the editor's corner names the three colors. A value node's socket (§4.3) has its input's type. Connections are not restricted by type: the engine converts between types (`01-architecture-overview.md` §2.1).

### 4.6 Managing processes

Implemented 2026-10-14 (plan task 32; decisions D1–D3 of §7). The process list shows the processes the engine has loaded, each with its running mark, its name, an **unsaved** mark (`network:status`'s `unsaved`, `02-wire-protocol.md` §3.3) and its actions — Start or Stop, Save (only when unsaved), Rename, Delete — always shown on the open process and on hover or focus on the others. Every action is a command; the list changes with the events.

- **Events the list needs** reach every client only as `network:status`: `network:started`/`stopped` and `graph:rename` reach only the process's subscribers (`02-wire-protocol.md` §4.1), and a process in the list need not be open. So Start, Stop and Rename are followed by a `network:getstatus` for that process, whose status (name, running, started, unsaved) every client receives. No protocol change.
- **Start / Stop**: `network:start`/`stop`. A start or stop makes the process unsaved when its started state differs from the saved one, and saving stores whether it starts at boot (D2).
- **Save** (D1): the Save button, or **Ctrl+S** for the open process, sends `network:persist`. The engine answers a successful save with the process's status, saved (`02-wire-protocol.md` §3.3), and the list shows a **short notice** ("Saved “…”", fading after 3 s). A failure is the broadcast `network:error` `"Unable to save graph: <name> (<id>)"`: for a save this client asked for, it is shown in a **dialog until it is dismissed** instead of with the other errors; the unsaved mark stays.
- **Rename**: in place in the list — a double-click on the name or the pen — Enter or leaving the field sends `graph:rename` when the name changed (any string is a valid name); Escape keeps it.
- **Delete**: asks first, naming the process ("Delete “…”? It is stopped, and its saved file is removed too."), then `runtime:delete_graph`. When the open process is deleted, the editor shows nothing.
- **New…**: the client picks the new process's id (a random UUID v4 from `crypto.getRandomValues`, which works on a plain-http page, unlike `crypto.randomUUID`) and sends it in `runtime:new_graph`; the process opens when its `runtime:new_graph` arrives.
- **The open process** also shows its uptime ("Running for 5 min", from `network:status`'s `uptime` and counting on while it runs, or "Stopped") and its description, read-only (D3).

### 4.7 Live values

Implemented 2026-10-14 (plan task 34). The values on the open process's inputs, from `network:edges`/`network:data` (`02-wire-protocol.md` §4.2). No protocol change.

- **Watching**: a connection or an input (its context menu, §4.4: *Watch value* / *Stop watching*), a block's inputs (*Watch inputs*), an input in the inspector (its ◉ toggle, §4.2), or **every connection of the process** (the canvas menu's *Watch all connections*, which also covers connections drawn later). Stopping the watch of a connection watched only through "watch all" turns "watch all" off. An input with a fixed value can be watched (its `src` is the input itself; the engine does not check `src`); an input without a source has nothing to show on the canvas, only in the inspector.
- **The set**: the client keeps the set of watched inputs and sends it whole as `network:edges` on every change (a request replaces the previous set, 02 §4.2), with each input's current source: a connection's output, else the input. It is sent again, after the events of a burst have been applied (50 ms), when a watched input gets or loses a connection, when "watch all" is on and connections change, and when a watched block is renamed (the engine's watches keep the names they were given) or removed. **Opening another process** clears the set (an empty one is sent); opening the same process again, also on a new connection, sends it again.
- **Showing a value**: as a label in the middle of the input's line — a connection, or a value node's line (§4.3) — and as "Live: …" under the input in the inspector. A value is shown as the engine sends it (a string), formatted by the port's type: a number with at most four decimals, a bool as it is, text quoted and cut to 24 characters. Until the first value arrives the inspector says "waiting…".
- **Stale values**: when the connection to the engine is lost, the values shown are marked stale (struck through, muted) until fresh ones arrive. Today a lost connection returns to the login screen; the mark matters once the view is kept while reconnecting (plan task 39).

### 4.8 Process ports

Implemented 2026-10-14 (plan task 35). A process's inputs and outputs (`graph:addinport`/`addoutport`, 02 §3.4), through which processes are linked (`01-architecture-overview.md` §2.2). No protocol change; the links themselves have no wire messages yet (`00-README.md` open question 13) and are not shown.

- **Exposing**: *Expose as process input…* in an input's context menu, *Expose as process output…* in an output's (a right-click on the output's row). A dialog asks for the public name, suggesting the port's own name (or `<block>_<port>` when the process already has a port of that direction so named), and sends `addinport`/`addoutport` (`public`); it stays open until the port's event arrives, and a refusal (`"Port exists: <name>"`, `"Invalid id"`, `"Unknown port"`, `"Not permitted: …"`) is shown in it, not with the other errors. Several ports may expose the same block port.
- **Markers**: each port is drawn as a marker with its public name — an input as an arrow-shaped tag **left of everything in the process**, an output **right of it** — level with its block port, with a dotted line to it; markers that would overlap move down, in their ports' order. They are placed again whenever a block or value node is added, moved or removed. Markers are not blocks: they are not selected or dragged, and their lines carry no live value (§4.7) and send nothing when drawn or pulled. A marker follows its block's renames and goes with its block (the engine removes the ports first, 02 §3.4).
- **Renaming and removing**: a marker's (or its line's) context menu has *Rename process port…* (the same dialog, `renameinport`/`renameoutport`) and *Remove process port* (`removeinport`/`removeoutport`).

### 4.9 Composite block types

Implemented 2026-10-14 (plan task 36; decided with the user: a type is defined as a component graph, `02-wire-protocol.md` §3.4.3). The group commands of §3.4.2 are not used by the frontend.

- **Creating one**: *Create composite type…* in a block's context menu (§4.4) — from the selection when the block is in it, else from the block alone. A dialog asks for the **type name** (suggested `user/…`; the palette's family is the part before `/`; a name a block type already has is refused before anything is sent), a description, and the **port mapping**: every input and output of the selected blocks is a row with a checkbox and the public name it gets in the type. Ticked at first, as `03-block-types.md` §5.2 does: an input fed by a connection from outside the selection, an output with a connection to outside it ("connected outside"), and a block port that is a process port (§4.8, under its public name). Names are suggested by §5.2's default names (the port's name; `<block>_<port>` for every port whose name two would share; then `<port>_<n>`); every name can be changed and any port ticked or unticked. Names are checked before sending (1–64 characters, no `.`, unique per direction). An exposed input's fixed value is not part of the type (the dialog says so): the type's input is fed from outside.
- **What is sent**: the type's component graph — `graph:clear` (`main: false`, the type name as its id), an `addnode` per selected block at its position, an `addedge` per connection between them, an `addinitial` per fixed value except on exposed inputs, an `addinport`/`addoutport` per ticked row — then `network:persist`. The type exists when its `component:component` arrives: the dialog closes and a short notice says so; it appears in the palette. A refusal (any `network:error` about the type's graph while it is built) is shown in the dialog and the half-built graph is deleted. The selected blocks are left as they were ("save as component").
- **Looking inside one**: a composite type's palette entry has an *open* button (↗) that opens its component graph like a process (`graph:connect`): its blocks, connections, fixed values and, as process port markers (§4.8), its ports; no process is marked open, and a banner names the type. The graph can be edited like a process; **Save type** persists it, which replaces the type — refused while an instance or another type uses it (`"Component in use"`, shown in the banner) — and **Delete type** (after a confirmation) removes the type and its file, also refused while it is in use. A deleted type leaves the palette (`runtime:delete_graph` of its graph).
- Not yet: renaming a type and changing its description from the frontend.

### 4.1 Themes

Decided 2026-10-14: the frontend's look comes from **pre-installed themes**, plain CSS files chosen by the viewer; there is no theme editor and no per-user setting in the engine.

- **What a theme is**: one stylesheet, `public/themes/<id>.css` (served as `/themes/<id>.css`, copied into the build as it is, not bundled), that sets **only CSS custom properties** — the `--hk-*` variables: page, surfaces, text, borders and their width, the accent and focus colors, errors, the running/stopped marks, and the editor's canvas, blocks, block titles, sockets, connections and minimap. `src/assets/hakkas.css`, bundled, styles every part of the UI from those variables and sets no color itself; it also restyles Rete's own parts (blocks, sockets, connections, minimap, context menu), whose built-in colors it overrides under the editor's id. A unit test checks that every installed theme sets exactly the variables `hakkas.css` uses.
- **The installed themes** are listed by `/themes/themes.json`, `[{"id", "name"}]` in the selector's order. Three are delivered: **Light**, **Dark** and **High contrast** (white and yellow on black, two-pixel borders, cyan connections). Since a theme is a file in `webdir`, another can be installed by adding its stylesheet and its entry in `themes.json`, without building the frontend; an id is 1–32 characters of `a–z`, `0–9` and `-`.
- **Choosing**: a selector next to Logout (shown when more than one theme is installed) switches at once. The choice is the **viewer's, per browser** (`localStorage`, key `hakkas.theme`): it is a viewing preference, not engine state, so it is not sent to the engine (02 §1.1 concerns the model, not the look). Without a choice — or when the stored theme is no longer installed, or storage is unavailable — the theme follows the system: High contrast when it asks for more contrast (`prefers-contrast: more`), else Dark or Light (`prefers-color-scheme`).
- **No flash**: `index.html` applies the theme with a few lines of inline script before the first paint, by the same rules as `src/theme.ts`; at startup `main.ts` then reads `themes.json` and replaces a stored theme that is no longer installed by the default, already on the login screen.

## 5. On the device

On Colibri (`04-drivers.md` §1) the frontend is stored on external flash: the MCU board carries a 16 MB W25Q128, mounted with LittleFS at `/mcu`, and the carrier board another, mounted at `/carrier` (`05-app-lifecycle-persistence.md` §1.3). The assets are plain files there, so the frontend can be updated without reflashing the firmware.

**Size**: the current bundle is about 4.0 MB, 2.5 MB compressed with gzip — mostly a JavaScript file of 2.1 MB (0.63 MB compressed) and Material Icons fonts in every style, 1.8 MB, which are already compressed; the styles are 12 KB and each theme about 1.5 KB (Bootstrap's 0.24 MB went with the themes, §4.1). That fits the flash comfortably, but it is written over SPI and every update rewrites it, so the bundle should shrink before the device ships: the 3D editor template pulls in three.js and is not used; the icon fonts are not used by any part of the UI yet; and the build can store each asset as `<file>.gz` only, which the web server serves to every browser (`05-app-lifecycle-persistence.md` §3).

## 6. Testing

Two suites, both in `frontend/tests/` (decided 2026-10-13):

- **Unit tests** (`tests/unit/`, Vitest, `npm test`, in Node without a browser or an engine): the protocol and model code. Messages enter through a real `Connection`'s dispatch (`onMessage`) with the socket left closed, and what it sends is recorded (`tests/unit/harness.ts`). They cover the themes (§4.1), the SCRAM computation, the resume key and proof, the login and resume handshakes (against a server side written with `node:crypto`, `tests/support/scram-server.ts`, independent of the frontend's `@noble/hashes` code), the kept session (§2), the WebSocket URL (§2), the client model fed by events (§3), new blocks' names (§4), the selection, a dragged selection's positions and their throttling (§4.0), what the inspector shows, which errors refuse a pending rename, and the fixed values' editors, parsing and refusals (§4.2), the value nodes' placement (§4.3), the context menus' items, the block search and moving through a menu (§4.4), and the palette's families, search and tooltips and the sockets' classes (§4.5), and the process list's uptime, failed saves and new ids (§4.6), and the set of watched inputs and the live values' formatting (§4.7), the process port markers' layout (§4.8), and a new composite type's default ports, name checks and commands (§4.9).
- **End-to-end tests** (`tests/e2e/`, Playwright, `npm run test:e2e`, which builds `frontend/dist` first): the built frontend in a browser against the real engine. **Each test starts its own engine** (`tests/e2e/fixtures.ts`): the `hakkas` executable (`HAKKAS_BIN`, default `build/debug/hakkas`, so the C build comes first) on free loopback ports, with a temporary configuration directory (a `hakkas.json` a test may extend, e.g. a short `auth.idle_timeout_s`), a users file with an editor and a viewer whose records the fixture computes with few PBKDF2 iterations, and the test's processes in `<datadir>/graphs/` (the sister project's `examples/example.json` by default). A test may also use a **second client** (`tests/e2e/protocol-client.ts`), a logged-in WebSocket client in Node, to act as another user or to observe what the frontend sent. Every test fails if the page reports an error or a graph event fails to apply, if the engine logs an error, or if it does not stop cleanly (exit code 0 after `SIGINT`); the engine's log is attached to the test's report. The suites cover the themes (switching, the choice kept across a reload, the default from the system, a theme no longer installed), login (success, refusals, retry, logout, session expiry, a lost connection, nothing secret in the console), resuming (reloads stay logged in, a logout or a session that cannot be resumed asks for the password without an error), rendering (§4, against the engine's own snapshot), and the command → event rule in both directions: another client's edits appear; the palette, dragging and drawing a connection reach the engine and come back as its events; a refused command (a viewer's) changes nothing and shows the engine's error; and selecting (clicks, the marquee, Escape, Ctrl+A, the canvas), dragging a selection and deleting it (§4.0); and the inspector against the engine's description of a type, with several blocks, following another client's rename and removal, renaming (the field, leaving it, F2, the block's menu, refusals at the field, Escape), and fixed values (connected/fixed/default, a number set and cleared, text that is not a number, a value sent when another block is clicked, a viewer's refusal at the input, the bool switch and the text field) (§4.2); the palette (search, a closed family opened by a search, tooltips, a click adding in the middle of the view, a drag adding at the drop point) and the sockets' colors by type with their legend (§4.5); managing processes (start and stop a process that is not open, uptime and description, the unsaved mark, Save and Ctrl+S with the notice and the file written, a failed save's dialog — the graphs directory made read-only — renaming in place, deleting after a confirmation, a new process opened) (§4.6); - **Browser**: Playwright's Chromium (`npx playwright install chromium`, once per machine), or any Chromium-based browser named by `HAKKAS_BROWSER` (e.g. an installed Chrome or Brave). Reports and failure artifacts (screenshots, traces) go to `frontend/test-results/`, which is not committed.

## 7. Not implemented yet

The order of the work is phase 5 of `docs/plan.md`. Decided with the user for it (2026-10-14):

- **Saving**: a Save button and an "unsaved" mark per process, from `network:status`'s `unsaved` (`02-wire-protocol.md` §3.3, a protocol addition). A successful save is confirmed discreetly (a short notice that fades); a failed one is shown prominently (a dialog, or an error that stays until dismissed). Implemented (§4.6, plan task 32).
- **Starting at boot** is the saved `started` state: the process list shows the loaded processes only (as now), each with start/stop; a start or stop makes the process unsaved, and saving it stores whether it starts at boot (`05-app-lifecycle-persistence.md` §2.1; `run daemon` starts the processes saved running; with `run processes` a list entry's own `start` wins, 05 §1.2). Implemented (§4.6).
- **A process's description** stays read-only in the UI for now (set at creation; no command changes it).
- **Composite types** are view-only for now: create, describe, rename and remove them, and look inside one; editing an existing type's inside is wanted in the long term and needs its own design (what happens to running instances). Revised with the user 2026-10-14 (plan task 36): a type is defined as a component graph (`02-wire-protocol.md` §3.4.3), so its inside is opened and saved like a process; a type in use cannot be replaced (§4.9).
- **Fewer logins**: reloading the page does not ask for the password again — the session is resumed with a resume key (`02-wire-protocol.md` §2.3.1, a protocol addition), kept in the browser's `localStorage` until the session would have expired or the user logs out. Implemented (§2, plan task 46).
- **Block categories**: the bitwise `math/And2` … blocks are gone and the comparisons are `compare/*` (`03-block-types.md` §3, plan task 47); the palette's sections are the type names' prefixes, so `compare` is a section of its own.

What the frontend does today is §2–§4: log in (and resume after a reload), list the block types and processes, open a process and draw it, and follow every change the engine broadcasts. Selecting blocks, moving and deleting the selection are §4.0, the inspector §4.2, value nodes §4.3, the context menus §4.4, the palette and the sockets §4.5, managing processes §4.6, live values §4.7, process ports §4.8, composite types §4.9. The other editing commands are sent from the editor's hooks: `addedge` and `removeedge`, by drawing and pulling lines. Missing, roughly in the order they are likely to be needed:
