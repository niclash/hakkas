# Hakkas — System Specification

## What this is

Hakkas is a flow-based-programming (FBP) runtime: users wire "blocks" (components with named, typed input/output ports) into a live dataflow graph. There is no separate edit/run mode — the graph is always running; structural changes (add/remove/connect/rename a block) and value changes take effect immediately, exactly like rewiring electronics while powered. A WebSocket protocol, a dialect of the FBP network protocol, lets a browser-based editor observe and mutate the running graph in real time. That frontend lives in the same repository (`frontend/`) and is specified in `06-frontend.md`; `02-wire-protocol.md` defines the exact wire contract between the two.

This directory specifies hakkas' design and behavior completely enough to implement it in C.

## Core principle: the engine owns the model, the UI only mirrors it

The frontend never updates its own view in response to its own actions. Every user action is sent to the engine as a command; the engine applies (or refuses) it and broadcasts the resulting event to every client that has the graph open, including the sender; each client updates its view only from those events. This keeps the engine's model and every open view in sync, including when several users edit the same graph at once. See `02-wire-protocol.md` §1.1.

## Target platforms

- **Primary**: MCUs with no general-purpose OS — RP2354 (RP2350 family) and possibly STM32H5/STM32H7/STM32N6 — running **Zephyr RTOS**, concretely the modular **Colibri** automation hardware (`04-drivers.md` §1: carrier boards with MCU, Comm and I/O slots), with the device hosting the full WebSocket/FBP server and serving the frontend's static assets directly.
- **Secondary build tree**: a POSIX/Linux-native build, used for Raspberry Pi deployment and for x86_64 development. It shares the entire portable core with the Zephyr build; see `01-architecture-overview.md` §0 for the Platform Abstraction Layer (PAL) boundary that makes this possible with only a small, isolated set of platform-specific files.
- Hardware bring-up on the Zephyr targets (devicetree, board support, peripheral drivers) is the responsibility of a separate effort; hakkas consumes Zephyr's device driver subsystem rather than talking to hardware registers directly. The device firmware provides the environment interface hakkas queries for the available inputs and outputs (`04-drivers.md` §1).

## Terminology

- **Process, block, connection** — hakkas' own terms, used in its file formats, its C API and this specification's new text: a **process** is one dataflow network, typically one automation function such as "hot water regulator" or "ventilation flow alarm"; it consists of **blocks** (instances of block types) and **connections** (a block output wired to a block input, or a literal initial). The FBP network protocol calls the same three things **graph**, **node** and **edge**; those names appear only on the wire (`02-wire-protocol.md`), whose command and field names follow the FBP protocol (e.g. `graph:addnode`, `{"node","port"}`), and in older text of this specification, where "graph" = process, "node" = block and "edge" = connection. One engine runs many processes at once; each can be started and stopped independently (`01-architecture-overview.md` §2.2).
- **Engine**: the always-running runtime that hosts every graph. The engine itself is never "stopped" while the system is up.
- **Initial** (FBP term): a literal value wired to a block input instead of a block output. See `01-architecture-overview.md` §2.2.
- **Group** / **composite block type**: the same thing — a user-selected subgraph, given a name and exposed ports, that becomes a reusable user-defined block type (`03-block-types.md` §5).
- **Change threshold**: the minimum change in a numeric output for it to be propagated downstream (`01-architecture-overview.md` §3.3).

## Protocol compatibility policy

The frontend already exists and already speaks a specific wire protocol. **Default policy: match it exactly** — `02-wire-protocol.md` specifies every message shape the frontend sends and expects, and the C implementation should honor that contract rather than "improve" it, since breaking it breaks a real client with no corresponding update planned.

**Exception**: in areas where the frontend has no real implementation today — most notably authentication (whose login handshake is redesigned, requiring a matching frontend change) and the group/composite-block commands — the wire shapes are free to be designed cleanly rather than contorted to match incomplete or unused client code. `02-wire-protocol.md` marks these areas explicitly. Protocol changes are always *allowed*, just *discouraged* by default; the bar for changing an area the frontend actively uses is much higher than for an area it doesn't yet.

**Since the frontend moved into this repository** (`06-frontend.md`, 2026-10-13), a protocol change and the matching frontend change could be made together, but the policy stays (user decision, 2026-10-13): the wire protocol is kept as close to the upstream FBP protocol as possible, so that `fbp-protocol.html` does not need updating. **Every protocol change is put to the user first**, one at a time; acceptable changes are typically additions (a new command, event or optional field), not changes to existing messages.

## Open questions (need your input before/while implementation)

1. **Raspberry Pi vs. x86_64 build tree specifics**: the POSIX build tree ("Target platforms" above) needs its own concrete choices — networking, timer facility, filesystem layout — beyond "mirror the Zephyr build's shape using POSIX primitives" (`01-architecture-overview.md` §0/§3.2.1). *Settled*: storage (plain files under the configured directories, atomic writes with `fsync` and directory sync), the clock (`CLOCK_MONOTONIC` since `pal_init`) and the random source (`getrandom()`) — `01-architecture-overview.md` §0.1; the file locations (`--confdir`, `--basedir`, `webdir`) — `05-app-lifecycle-persistence.md` §1.1–§1.2. Timers are settled for both build trees: there is no OS timer facility at all — timers are deadlines kept by the portable core, and the event loop's `poll()` timeout is the only timing primitive (`01-architecture-overview.md` §3.2 item 7). Networking is settled (plan task 12): plain non-blocking BSD sockets and `poll()`, numeric IPv4/IPv6 addresses, an `eventfd` wakeup for the cross-context enqueue, `MSG_NOSIGNAL`, `SIGINT`/`SIGTERM` as stop requests (`01-architecture-overview.md` §0.2, §3.2.1). Every part of this question is now decided.
2. **EEPROM module-descriptor format**: *decided — dropped.* The hardware platform it was written for no longer exists; no EEPROM is involved. Instead the environment (device firmware on Zephyr, a simulator on POSIX) provides a service provider interface that hakkas queries for the available external inputs and outputs, described like block types but not instantiable (`04-drivers.md` §1). Binding graph ports to them is open question 3; their representation is open question 6. Implemented in plan task 22: the SPI's C types (`src/hakkas_env.h`) and the engine's side in `04-drivers.md` §0.
3. **Binding graph ports to the environment**: *decided* (`04-drivers.md` §1, §4). A **bindings file** per process and environment, paired with its process in `processes.json`, maps block ports to environment channels: `{"environment": "<name>", "bindings": [{"block", "port", "env", "index"?}]}`. A binding is a connection: a sensor (an environment output port) binds a block input as its one source; an actuator (an environment input port) binds a block output, with one driver per actuator channel across the deployment. Graph-side problems (unknown block/port, direction, fan-in, a second driver, a mismatched environment) refuse startup; a channel the environment doesn't provide is skipped with a warning and stays inert. The sister project's `examples/bindings-emulator.json` was an early sketch and is not authoritative. Implemented in plan task 22 (`04-drivers.md` §4 "Implementation decisions"): applied by the POSIX host when it loads a process from its process list, all or nothing; a sensor-bound input whose binding is removed reverts to its default, like any severed input; the C API's binding commands and events (`02-wire-protocol.md` §6), with no wire message yet.
4. **Group / composite creation mechanism**: *decided* — **"save as component"**. Creating a group from a selection builds and registers a new composite block type (`03-block-types.md` §5.2) and leaves the selected blocks unchanged; the user replaces them by an instance manually if they want to. This keeps the action simple and predictable for the user. A separate "collapse" option (replace the selection by an instance) may be added later. The wire commands are those of `02-wire-protocol.md` §3.4.2. Graph-level inports/outports, which this question also mentioned, are now part of open question 13 (linking processes).
5. **PID and schedule block parameters**: *PID decided* (`03-block-types.md` §6.1, revised 2026-10-13): parallel form `Kp`/`Ki`/`Kd`, direct/reverse acting, derivative on measurement limited by a max D gain, output min/max with conditional-integration anti-windup, bumpless manual/auto, a `saturated` output; built in now, possibly refined later with the user's own PID code. *Schedules decided* (`03-block-types.md` §6.2): small calendar primitive blocks with their settings on input ports (`timing/MinuteRange` with a `"12:30-15:45"` string, `timing/DayOfWeek` 1–7 with a Sunday-first flag, `timing/MonthOfYear` 1–12, and e.g. `DayOfYear`, `WeekOfYear`, `HolidaysOfSweden`), each with a bool output; the industry's standard schedule types are delivered as built-in composites of them. Block metadata is UI-only and never drives live function (`01-architecture-overview.md` §2.2). Selector strings (`"1-5"`, `"6,7"`, `"1-3,5"`), `MinuteRange` end exclusive with wrap past midnight, ISO 8601 week numbers, `logic/And`/`Or`/`Not`/`Xor` with bool outputs, and the schedule composites supplied as an optional **standard library** of type files rather than built in. Every part of this question is now decided. Implemented in plan task 24 (`03-block-types.md` §6.2: also `timing/DayOfMonth`; the library is `library/schedules/` in the repository); `timing/HolidaysOfSweden` waits for the user's list of the days that count.
6. **Representing the hardware environment**: *decided* (`03-block-types.md` §4). Graphs contain no hardware blocks — the `io/*` block types are dropped. The environment describes its inputs and outputs like a block type that cannot be instantiated (`04-drivers.md` §1), and a bindings file connects ordinary block ports to them (open question 3); the frontend lets users hide and organize environment ports, which they cannot create or delete. A physical output **keeps its last value** whenever no running process drives it (not loaded, stopped, unbound) — hakkas does nothing; a release timeout (e.g. 1–10 minutes) may come later. Watchdog behavior on crash, on Zephyr or in hardware, is out of scope.
7. **Change threshold semantics**: *decided* (`01-architecture-overview.md` §3.3). The threshold stays absolute, resolved from the block type's default, then the engine-wide default. The per-block override in node metadata is **removed** (metadata is UI-only); there is no relative threshold and no per-output override in the engine. Instead a **`process/Deadband`** block (inputs `in`, `threshold`; output `out`) is placed in the line where a signal needs different filtering (`03-block-types.md` §3); a `relative` input may be added later.
8. **Numeric edge cases in type conversion**: *decided* (`01-architecture-overview.md` §2.1) — conversions to integers saturate: NaN → 0, out-of-range → the nearest bound, and `to_u64` of any negative value (double or integer) → 0.
9. **`Metric` arithmetic**: *decided — `Metric` is dropped* (`01-architecture-overview.md` §2.1). Port values are plain numbers; units are UI information in port descriptions (e.g. the environment's), and remapping a measurement is done with a block such as `process/Linear`. The per-block error flag goes with it.
10. **Work-queue capacity formula**: *decided* — the work queue has a fixed capacity set per build (default 1024 entries, `01-architecture-overview.md` §3.2), predictable on an MCU; overflow drops the oldest entry and logs a rate-limited warning. Sizing it from the number of wires is revisited only if those warnings show up in practice.
11. **Wall-clock time**: *decided*. The wall clock is provided by the environment's service provider interface (`04-drivers.md` §1); how the environment obtains it (SNTP, RTC, the host OS) is the environment's business. It is UTC, as is everything stored or sent; the calendar blocks evaluate in local time from the engine-wide `time_zone` POSIX TZ string in `hakkas.json` (`05-app-lifecycle-persistence.md` §1.1), with defined daylight-saving edge rules (`03-block-types.md` §6.2). Implemented in plan task 22: the wall clock is the environment's `wall_ms`, with the PAL's `pal_wall_ms()` (plan task 24's interim source) as the fallback without an environment or without its `wall_ms`; wire timestamps are real UTC from it (`02-wire-protocol.md` §3.3); a step of the wall clock re-evaluates the calendar blocks at once (`01-architecture-overview.md` §3.4, plan task 24).
12. **Graph auto-start**: *decided — hakkas does not manage process lifetime.* The **host** that embeds the hakkas runtime decides which processes are loaded and when they start: on POSIX, `main.c` (command line, process list `processes.json`); on Zephyr, whatever creates the runtime. Hakkas exposes the WebSocket protocol's commands and events locally as a **C API** (`02-wire-protocol.md` §6), so the host loads, starts and stops processes and monitors their lifecycle events exactly like a client does. The engine no longer acts on a graph file's `started` flag; it is information for the host. The C API is **typed** — C functions and event structs — layered, like the WebSocket dispatcher, over the same model command layer so validation, refusals and events cannot drift (`02-wire-protocol.md` §6). Implemented in plan task 21e: the header `src/hakkas.h`; the POSIX host's commands, process list and start policy are in `05-app-lifecycle-persistence.md` §1.2.
13. **Linking processes together**: *decided* (`01-architecture-overview.md` §2.2, `05-app-lifecycle-persistence.md` §1.2). Processes exchange values through their graph-level **outports and inports**, which form each process's interface. Links are declared **explicitly at deployment level, in `processes.json`**, as `{"from": "<process>.<outport>", "to": "<process>.<inport>"}` (process = graph id), keeping each process self-contained and portable, like bindings files do for the environment. A link carries values like any edge (the same work queue, the source block's change threshold, no fan-in). If the source process is stopped, the linked input keeps its last value; if the source isn't loaded or the link is removed, the input reverts to its default. Implemented in plan task 21f: the model and its lifecycle (a linked port removed or renamed ends the link; a process may link to itself) in `01-architecture-overview.md` §2.2, the C API (`hakkas_link_add`/`_remove`, link events) in `02-wire-protocol.md` §6, and the POSIX host making a process list's links after loading and before starting (`05-app-lifecycle-persistence.md` §1.2). *Still open*: the wire commands and messages for links (the UI sees nothing of a link yet but its values), and how a link made at runtime — from the UI or the C API — is persisted into the host's `processes.json`.
14. **Where the files live on Colibri**: *decided* (2026-10-13; `05-app-lifecycle-persistence.md` §1.3). The device has two 16 MB W25Q128 flash chips with LittleFS, `/mcu` on the MCU board and `/carrier` on the carrier board: the frontend in `/mcu/web` (it goes with the firmware), the configuration directory `/carrier/config` (`hakkas.json`, `users.json`) and `datadir` `/carrier` (`graphs/`, `types/`) (they describe the installation and stay with the carrier board when the MCU board is replaced). Nothing implements these paths yet (the Zephyr port is plan task 25).
15. **Alarms**: *decided* (2026-10-15, `03-block-types.md` §7.1). `process/Alarm` with the states `Normal`, `Activated`, `Deactivated`, `Reactivated`, `Acknowledged`, `Disabled`, `Blocked` and their transitions; unblocking or enabling goes to `Normal`, then evaluates `input`; `Disabled` wins over `Blocked`; the input is `disable`, not `enable`, so a new alarm is enabled. Classes are `A`–`D`; since inputs have no per-port defaults and a value over a connection cannot be refused, any other value (the unset `""` included) is read as `C`, and the frontend will offer only the four. Further alarm details are to be documented later.
