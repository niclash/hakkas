# 05 — Startup, Configuration, Persistence, Web Server, Logging

## 1. Configuration and startup

### 1.1 Configuration file

Both build trees read one JSON configuration file, `hakkas.json`:
- POSIX: `<confdir>/hakkas.json` (`--confdir`, default `/etc/hakkas`);
- Zephyr: `/lfs/config/hakkas.json` on the LittleFS partition.

Every key is optional; a missing key takes the default below, and a missing file means "all defaults". On the POSIX build, command-line options (§1.2) override the file.

| Key | Default | Meaning |
|---|---|---|
| `engine_id` | *(unset → a random UUID each boot)* | Engine identity, reported as `id` in `runtime:runtime` (`02-wire-protocol.md` §3.2) and in mDNS TXT records. |
| `label` | `"Hakkas"` | `label` in `runtime:runtime`. |
| `host` | `"0.0.0.0"` | Address both listeners bind to. |
| `port` | `8080` | Web server port (static assets). The FBP WebSocket listens on `port + 1` (`02-wire-protocol.md` §0). |
| `webdir` | POSIX: `<cwd>/frontend/src`; Zephyr: `/lfs/web` | Location of the frontend's static assets. |
| `datadir` | POSIX: `<basedir>`; Zephyr: `/lfs` | Parent directory of `graphs/` and `types/` (§2.3). |
| `max_connections` | `4` | Maximum concurrent WebSocket connections. |
| `max_message_bytes` | `16384` | Maximum WebSocket message size (all fragments of a message together; `02-wire-protocol.md` §0). |
| `allowed_origins` | `[]` | Extra `Origin` values accepted on the WebSocket upgrade, besides the device's own (`02-wire-protocol.md` §0). |
| `change_threshold` | `0.05` | Engine-wide default change threshold (`01-architecture-overview.md` §3.3). |
| `log.level` | `"warn"` | `fine`, `info`, `warn`, or `error` (§4). |
| `log.mirror` | `false` | Mirror log output to authenticated clients as `network:output`/`network:error` (§4). |
| `auth.users_file` | POSIX: `<confdir>/users.json`; Zephyr: `/lfs/config/users.json` | Credential store (`02-wire-protocol.md` §2.2). |
| `auth.idle_timeout_s` | `1800` | Session idle timeout (`02-wire-protocol.md` §2.5). |
| `auth.max_lifetime_s` | `43200` | Session absolute lifetime. |
| `auth.server_secret` | *(generated on first boot and written back to the file)* | Random key used to fake challenges for unknown users (`02-wire-protocol.md` §2.3). |
| `tls.enabled`, `tls.cert`, `tls.key` | `false`, —, — | Optional TLS on both ports (`02-wire-protocol.md` §2.5 item 9; not implemented yet: `true` refuses startup, `02-wire-protocol.md` §0). |
| `net.hostname` | `"hakkas-<last 3 MAC bytes in hex>"` | mDNS hostname (Zephyr; `04-drivers.md` §6). |
| `net.dhcp`, `net.address`, `net.netmask`, `net.gateway` | `true`, —, —, — | IPv4 configuration (Zephyr only; the POSIX build uses the host OS's network configuration). |

The file is written (when `auth.server_secret` is generated) using the same atomic-write procedure as every other persisted file (§2.3).

Implementation decisions (plan task 11, `src/system/config.h`):
- **Nested keys**: a key `<section>.<key>` of the table is the member `<key>` of the object `<section>` (`log`, `auth`, `tls`, `net`), e.g. `{"log": {"level": "info"}}`. A top-level member literally named `"log.level"` is an unknown key.
- **Missing file**: all defaults (noted at `info`). Every key is optional, and a key whose value is `null` is the same as an absent key (also a whole section).
- **Malformed file → the engine refuses to start** with an error: text that is not a JSON object (or has anything but whitespace after it), nesting deeper than cJSON's limit (`third_party/cjson/README.md`), a file larger than `HAKKAS_CONFIG_FILE_MAX` (16 KiB, a per-build override), or a duplicate key at the top level or within a section.
- **Unknown keys** (also within a section) are logged as a warning and ignored, for forward compatibility.
- **Invalid values → the engine refuses to start**: every key with the wrong type or an out-of-range value is logged as an error naming it (`<file>: <key>: expected …`; the value itself is never logged), all of them, then startup stops. Valid values: `engine_id` a string of 1–64 bytes; `label` 0–64 bytes; `host` 1–63 bytes (not otherwise checked here; the listeners take only a numeric IPv4 or IPv6 address, `01-architecture-overview.md` §0.2, so a host name fails when they open in startup step 8 and the engine refuses to start); `port` an integer 1–65534 (`port + 1` must be a port too); `max_connections` an integer 1–1024; `max_message_bytes` an integer 1024–16777216; `allowed_origins` an array of at most 8 strings (`HAKKAS_CONFIG_ORIGINS_MAX`, a per-build override) of 1–127 bytes; `change_threshold` a number ≥ 0, `1e999` (+Infinity) included (`01-architecture-overview.md` §3.3); `log.level` one of the four names; `log.mirror`, `tls.enabled`, `net.dhcp` booleans; `auth.idle_timeout_s`, `auth.max_lifetime_s` integers 1–2147483647; `auth.server_secret` a string of 16–128 bytes; `net.hostname` 1–63 letters, digits and inner `-` (one DNS label); `net.address`/`netmask`/`gateway` a dotted-quad IPv4 address or `""` (none); a section a JSON object; paths below. An integer may be written in any JSON number form with an integral value (`8.0e3`).
- **Paths** (`webdir`, `datadir`, `auth.users_file`, `tls.cert`, `tls.key`): a relative path in the file is relative to the configuration directory (the file's own directory); a path given as a command-line option (§1.2) is used as given, i.e. relative to the working directory. A path (after that) is at most 251 bytes (`PAL_PATH_MAX` minus room for an atomic write's `.tmp`, §2.3). `webdir`, `datadir`, `auth.users_file` must not be empty; `tls.cert`/`tls.key` `""` means none (the default). The platform supplies the defaults that depend on it (configuration directory, `webdir`, `datadir`); the core derives the configuration file `<confdir>/hakkas.json` and the default users file `<confdir>/users.json` from the configuration directory (`/lfs/config` on Zephyr).
- **`engine_id`** unset: a fresh random UUID v4 (lowercase, the generator of `runtime:new_graph`'s ids, `src/system/uuid.h`) at every boot, after the command-line overrides.
- **`net.hostname`** `""` (the default) means the platform's default, `hakkas-<last 3 MAC bytes in hex>` on Zephyr.
- **`auth.server_secret`**: generated as 32 bytes from the PAL's random source, encoded in base64 (RFC 4648 §4: standard alphabet, `=` padding, 44 characters). The HMAC key of `02-wire-protocol.md` §2.3 is the string's bytes as stored, not decoded, so a hand-written secret is any string of 16–128 bytes. Only the startup of `run` (§1.4 step 1, plan task 19) generates and writes it; the other commands never write the file. It is written back by inserting the member as text — as the first member of the `auth` object, which is created if absent (a `null` `auth` or `server_secret` is replaced) — so every other byte of the user's file (formatting, key order, numbers, unknown keys) stays as it was. A missing file is created holding only the secret (mode `0600` on POSIX, like every file `pal_storage_write` creates). If the file cannot be written (e.g. the configuration directory is missing or read-only), the engine refuses to start. The secret is never logged (`02-wire-protocol.md` §2.5 item 8).
- **Base64**: encoded with mbedTLS's encoder through `src/system/crypto.h` (plan task 15, `01-architecture-overview.md` §6), which replaced plan task 11's own encoder with the same output.

### 1.2 POSIX build tree (Raspberry Pi, x86_64 development)

A command-line tree configures and starts the runtime:

- Global options: `--fine`/`--info`/`--warn` (log verbosity, most-to-least verbose; overrides `log.level`), `--basedir <dir>` (default `.`), `--confdir <dir>` (default `/etc/hakkas`).
- `list types` — print every registered block type name.
- `describe type <typename>` — print one block type's JSON descriptor: the `component:component` payload (`02-wire-protocol.md` §3.5).
- `describe topology <filename>` — load a graph file standalone and print its JSON description: the graph's canonical form (§2.1).
- `user add <name> --role <role>`, `user passwd <name>`, `user del <name>`, `user list` — manage the credential store (`02-wire-protocol.md` §2.2).
- `run [options] process <filenames>` — start the engine and load the given colon-separated list of graph files, in order.
- `run [options] daemon` — start the engine and load every graph in `<datadir>/graphs/`.
- **Process list** (requirement, to be implemented): a JSON file listing the processes (graphs) to load into memory and run, in the shape of the sister project's `examples/processes.json` (an array of graph file paths). It is also where each process will be paired with its bindings file (`00-README.md`, open question 3). Its location, path resolution and relation to `run daemon` are decided when it is implemented.
- `run`'s own options override the corresponding configuration-file keys: `--id <id>` (`engine_id`), `--webdir <dir>`, `--host <addr>`, `--port <n>`, `--users <file>` (`auth.users_file`).

Implementation decisions (plan task 11, `src/platform/posix/cli.h`):
- **Grammar**: `hakkas [global options] <command>`. Global options come before the command and also include `--help`/`-h` (usage on stdout) and `--version`; `run`'s options come between `run` and `process`/`daemon`. An option's value is the next argument (no `--opt=value`), must not be empty, and a repeated option takes its last value. `user add` takes the name and `--role <role>` in either order.
- **Configuration**: every command except `--help`/`--version` first builds the configuration — defaults < `<confdir>/hakkas.json` < options — so an unreadable, malformed or invalid file fails every command, not only `run`. `datadir` defaults to `--basedir`, `webdir` to `<working directory>/frontend/src`. `--fine`/`--info`/`--warn` already apply while the file is read; the resulting `log.level` is the log threshold.
- **Output**: results (type names one per line, a compact JSON document on one line) go to stdout; diagnostics go through the log (§4), whose POSIX sink is stderr.
- **Exit codes**: `0` success (for `run`: the engine stopped cleanly after a stop request); `1` a runtime failure (configuration file, unknown type, a graph file that does not load, an unknown or already existing user, a refused password, a malformed or unwritable users file, an engine that refuses to start); `2` a usage error (unknown command or option, a missing or extra argument, an invalid option value such as `--port 0`, an invalid user name or role for `user add`, a missing `--role`).
- **User commands** (plan task 16): they edit `auth.users_file` (default `<confdir>/users.json`; a missing file is no users, and `add` creates it). `add` creates a user with the role (`admin`, `editor`, `operator`, `viewer`; required; a name that exists is refused); `passwd` sets an existing user's password, keeping the role; `del` removes a user; `list` prints `<name> <role>` per user, one per line, in file order, and nothing else. A malformed users file is never overwritten: the command fails (`02-wire-protocol.md` §2.2). The file is written atomically (§2.3). A running engine re-reads it whenever it makes a login challenge (decided, plan task 18, `02-wire-protocol.md` §2.2), so a change takes effect at the next login, without a restart; sessions already open are not affected.
- **Passwords** (`add`, `passwd`) are read from standard input, never from argv. When it is a terminal: a prompt on stderr, echo turned off while the line is read straight from the descriptor (so no stdio buffer keeps a copy), the password asked twice and both entries must match; `SIGINT`/`SIGTERM`/`SIGQUIT`/`SIGTSTP` while echo is off restore the terminal before taking effect. When it is not a terminal (a pipe or file, for scripts and tests): one line is read, without a prompt or confirmation. The line ends at a newline (a CR before it is dropped) or the end of input; an empty password, no input and more than 1024 bytes are refused. Password buffers are zeroized after use.
- **`run`** (plan task 19, `src/engine/engine.h`): builds the configuration like every command, then runs the startup sequence of §1.4 (the portable `engine_start`, shared with the Zephyr port), the engine loop until `SIGINT` or `SIGTERM` (the stop request, `01-architecture-overview.md` §0.2), and the shutdown. It exits `0` after that clean stop and `1` if the engine refuses to start (every such cause is logged as an error, followed by `the engine did not start`). `run process` refuses to start when any of its files does not load; `run daemon` skips such a file (§1.4 step 7). The built-in block types are registered by the engine (§1.4 step 4), not by the command line as for the other commands.

### 1.3 Zephyr build tree (MCU targets)

There is no argv to parse at boot. Configuration comes from Kconfig (compile-time limits and features), devicetree (board topology), and the configuration file on LittleFS (§1.1). The device always behaves like `run daemon`. An equivalent of the `list types`/`describe type`/`describe topology`/`user …` commands is exposed through Zephyr's shell subsystem over a console/USB-CDC backend, for interactive diagnostics and for provisioning users.

### 1.4 Startup sequence (both build trees)

1. Read the configuration file and apply command-line overrides (POSIX) → initialize logging and file locations. On Zephyr, first mount LittleFS.
2. Initialize the PAL: clock, random source, storage; on Zephyr also bring up networking (`04-drivers.md` §6). Delete any leftover `*.tmp` files from an interrupted write (§2.3). Create the engine loop (`loop_init`, which opens the PAL's cross-context handoff, `01-architecture-overview.md` §0.2) before step 5 starts any IO worker; on POSIX, install the `SIGINT`/`SIGTERM` stop handlers.
3. Load the credential store and initialize the authorization component (`02-wire-protocol.md` §2). A missing, empty, malformed or unreadable users file never refuses startup: the engine runs with no users and every login is refused (`users_load_startup`, `02-wire-protocol.md` §2.2). The authorization component's tick hook (session expiry, delayed challenges, `auth_tick`) is added to the loop (`loop_add_tick`). The authorization component is given the users file as its reader (`AuthConfig.load_users = users_loader`, its path as context) and re-reads it at every challenge (`02-wire-protocol.md` §2.2: missing, empty or malformed → no users, as at startup; unreadable → the previous users kept).
4. Register every built-in block type (`03-block-types.md`).
5. Initialize the IO provider: discover and configure hardware modules on Zephyr, or set up simulated channels on POSIX (`04-drivers.md` §0–§1).
6. Load composite block types from `<datadir>/types/` in dependency order: repeatedly register every type whose inner types are all registered, until no more can be registered. Anything left over (an unknown inner type, or a cycle) is logged as an error and skipped.
7. Load the configured graph files (POSIX `process`) or every graph in `<datadir>/graphs/` (POSIX `daemon`, Zephyr). Start each graph whose persisted `started` flag is `true` (§2.1).
8. Open the web server on `port` (`web_server_open_config`, §3) and the FBP WebSocket listener on `port + 1` (`ws_server_open_config`, `02-wire-protocol.md` §0), both on `host`; if either cannot be opened, the engine refuses to start (also when `tls.enabled` is set: TLS is not implemented yet).
9. Enter the engine loop (`01-architecture-overview.md` §3.2, §3.2.1). It runs until a stop request (POSIX: `SIGINT`/`SIGTERM`), then closes every connection and listener and returns.

Implementation decisions (plan task 19, `src/engine/engine.h`; the POSIX command line calls it for `run`, §1.2):
- **One portable sequence**: steps 1–9 are `engine_start` (1–8), `engine_run` (9) and `engine_stop` (the shutdown), written once against the PAL and the core modules. The platform supplies what is its own: logging's console sink, the configuration with its overrides (step 1's reading), and two hooks around the loop — POSIX installs its stop signal handlers right after `loop_init` and restores them at shutdown before `loop_deinit` (which closes the wakeup a handler writes to).
- **The PAL is initialized before step 1** (`pal_init`), by the platform (POSIX: `main`, before the command line), since reading the configuration goes through it; step 2 is the rest. On Zephyr, bringing up networking needs the `net.*` keys, so it follows the configuration (plan task 25).
- **Step 1**: the log threshold is `log.level`; `engine_id` is generated if unset and `auth.server_secret` generated and written if absent (§1.1); a secret that cannot be written refuses startup.
- **Step 2**: `<datadir>/graphs/` and `<datadir>/types/` are created if missing (§2.3); if that fails (e.g. `datadir` does not exist) the engine refuses to start, since nothing could be persisted. Then the `*.tmp` cleanup of §2.3 step 4 in those two directories and in the configuration file's and the users file's directories (once if they are the same); a missing directory has nothing to clean, any other failure is logged as a warning and startup goes on.
- **Step 5** does nothing yet: the IO provider is plan task 22.
- **Step 6** (decided, plan task 21; `type_files_load_all`, `src/app/type_files.h`): every regular file ending in `.json` in `<datadir>/types/` (so no `.tmp` leftover) is read and parsed first; then in rounds, each round goes through the remaining files in byte order of their names and registers every type whose inner types are all registered, until a round registers none. A file that cannot be read (or is larger than `HAKKAS_TYPE_FILE_MAX`, 64 KiB by default, a per-build override), is not one JSON object, or is refused when its inner types are all there (any refusal of `03-block-types.md` §5.1) is logged as an error and skipped. What is left after the last round — an unknown inner type, a cycle, a type naming itself, or a dependency on a skipped type — is logged as an error with the registration's message (`"Unknown component: <type>"`, noting when that type is another file that did not load either, or `"Recursive component: <name>"`) and skipped. A file whose name is not the encoding of its type's name is loaded with a warning. Step 6 never refuses startup, in either mode; the info line `<n> composite type(s) loaded` follows. Nothing is broadcast (no client yet). At shutdown the composite types are unregistered after the graphs are destroyed, before the built-in types.
- **Step 7 failures** (decided, plan task 19): `run process` loads only the files the user named, so **any file that does not load refuses startup** (each failure logged, then `run process: a graph file did not load`). `run daemon` (and Zephyr) loads whatever is in `<datadir>/graphs/`: a file that does not load is logged and skipped, and the engine runs with the others — one corrupt file must not stop every other graph controlling the plant. A file that loads with skipped entries (§2.2) is loaded in both modes. Graphs start with the engine time read just before loading, which the loop then carries on.
- **Step 8**: the protocol layer (`protocol_create`), then the web server and the WebSocket listener; any failure — a port in use, a host that is not a numeric address, `tls.enabled` — refuses startup.
- **Ready**: one `info` line, `engine <engine_id> ready: web server on <host> port <port>, WebSocket on port <port + 1>`. The server secret is never logged.
- **Shutdown** (after the loop returned, having closed every connection and listener): the web and WebSocket servers, the protocol layer, the authorizer's tick hook and the authorizer, the platform's hook, the loop, the graphs (destroyed without events; **nothing is saved at shutdown** — a graph's file changes only through `network:persist`, so a running graph's started flag is the persisted one at the next boot), the runtime, the composite block types, the built-in block types. A step that fails during startup releases everything made before it.
- **Tests only**: `engine_start` can put both listeners on ephemeral ports (a parameter, not a configuration value), so `port` keeps its 1–65534 range for real use.

## 2. Persistence

### 2.1 Graph file format

One canonical JSON schema is used for both loading and saving a graph. Saving a loaded graph reproduces the same graph: the same blocks, connections, metadata, and ports.

```json
{
  "id": "...", "name": "...", "description": "...", "icon": "...",
  "started": true,
  "blocks": {
    "<instance-name>": { "component": "<type-name>", "metadata": { "x": 0, "y": 0 } }
  },
  "connections": [
    { "src": {"node":"<block>","port":"<port>"}, "tgt": {"node":"<block>","port":"<port>"}, "metadata": { "route": 3 } },
    { "src": {"data": <value>}, "tgt": {"node":"<block>","port":"<port>"} }
  ],
  "inports":  [ { "name": "...", "node": "...", "port": "..." } ],
  "outports": [ { "name": "...", "node": "...", "port": "..." } ]
}
```

- `started` is the graph's started/stopped state when it was persisted; it is restored at boot (`00-README.md`, open question 12). It defaults to `false` if absent.
- `blocks` is an object keyed by instance name; each value's `component` names a registered block type. `metadata.x`/`metadata.y` are the canvas position (default `50,50`). Any other metadata keys are preserved as-is (metadata is UI-only; a `change_threshold` key from older files is an ordinary opaque key, `01-architecture-overview.md` §3.3).
- `connections` entries are either a normal edge (`src`/`tgt` both reference `{node, port}`, with optional opaque UI `metadata`) or an initial (`src` is `{"data": <value>}`, stored as a native JSON string, number, or boolean — `02-wire-protocol.md` §3.4).
- `inports`/`outports` declare the graph-level named ports that a group built from this graph would expose (`01-architecture-overview.md` §2.2).
- Groups are not stored in the graph file: a group is a block type, stored in `types/` (§2.3, `03-block-types.md` §5.1).

Implementation decisions (plan task 10, `src/app/graph_files.h`):
- **Canonical form**: a save writes compact JSON (no whitespace) with the top-level keys in the order of the example and every key present (`description`/`icon` `""`, empty `blocks`/`connections`/`inports`/`outports`). Blocks are in creation order; each block's `metadata` has `x`, `y`, then its other keys in their order. Connections are listed per target block (creation order) and input (port order) — its initial or its edge — followed by the retained connections of placeholder blocks (§2.2) in load order. Graph ports: the live ones in creation order, then the retained ones.
- **Numbers are exact**: every number is written in `linkable_stringify`'s f64 form (the shortest text that reads back to the same double, `01-architecture-overview.md` §2.1, §6), opaque metadata included; an infinite `change_threshold` or opaque number is written `1e999`/`-1e999`.
- **Initial values** in `src.data`: a string and a boolean natively; a finite f64 as a JSON number; a non-finite f64 as the string `"NaN"`, `"Infinity"` or `"-Infinity"` (JSON has no such numbers), which a `"number"` port parses back to the same value (`02-wire-protocol.md` §3.4); a `Metric` as its string form `"<value> <unit>"`, which a `"number"` port parses back into a `Metric`; an i64 as its exact JSON integer text — it reads back as an f64, like every JSON number (`02-wire-protocol.md` §3.4; an i64 initial can only come from the C API, never from the wire or a file).
- **Round trip**: saving is a fixed point of loading. A file written by this code loads into a graph that saves to the same bytes; the first save of any other valid file is its canonical form — the same graph, in the order above, with numbers in their shortest exact form and initials in the type they were parsed into (`"5"` on a `"number"` port is written back as `5`, an integer beyond 2^53 as its nearest double).

### 2.2 Loading rules

- Each block's `component` is resolved against the block type registry. An unresolvable type name produces a **placeholder block**: it logs a warning, has no ports, and takes part in no dataflow. It keeps its original `component` name, metadata, and every connection that referenced it, and writes them back unchanged on save, so loading a graph on a system that lacks a type never destroys data. The one exception is an explicit user edit: a live edge or initial wired to an input that a retained connection feeds, or a live graph port taking a retained port's name, replaces the retained entry (`01-architecture-overview.md` §2.2), since the model never holds a fan-in.
- A connection that violates the graph's invariants (unknown node or port, fan-in) is logged and skipped, exactly as the equivalent wire command would be refused (`02-wire-protocol.md` §3.4.1).
- Initials are applied as their connections are loaded; the graph starts (if `started`) only after the whole file is loaded.

Implementation decisions (plan task 10, `src/app/graph_files.h`):
- **Reading**: a file is read through the PAL into one buffer sized from `pal_storage_stat`. A file larger than `HAKKAS_GRAPH_FILE_MAX` (default 256 KiB, a per-build compile-time override; the parsed tree takes several times the file's size) is refused before anything is read.
- **Malformed files are refused as a whole**, logged as an error, with nothing created. The minimum valid document is a JSON object (nothing but whitespace after it) whose `id` is a valid graph id (1–64 bytes, `02-wire-protocol.md` §3.4.1). `name`, `description` and `icon` must be strings, `started` a boolean, `blocks` an object, and `connections`, `inports`, `outports` arrays; each may be absent (`name` defaults as in `runtime:new_graph`, the others to `""`, `false` or empty). Text that is not JSON, nested deeper than cJSON's limit (`third_party/cjson/README.md`), or any other shape is malformed. A file whose `id` is already loaded is refused too (`Graph exists`).
- **Entries are loaded one by one** through the same registry commands as the wire (`runtime:new_graph`, `addnode`, `addedge`, `addinitial`, `addinport`/`addoutport`), so an entry is refused exactly as the command would be, logged as a warning with the command's message (`02-wire-protocol.md` §3.4.1), and skipped; the rest still loads. Besides those refusals an entry is skipped when it has the wrong shape: a block that is not an object with a string `component`, or whose `metadata` has a non-numeric (or non-finite) `x`/`y`; a connection whose `src`/`tgt` are not `{node, port}` strings or `{data}` with a string, number or boolean, or whose edge `metadata` is not an object; a graph port that is not `{name, node, port}` strings. Fan-in: the first connection to an input wins, live or retained. Only running out of memory aborts a load, and then the partly loaded graph is deleted.
- **Placeholders**: an entry whose block is a placeholder is kept as a retained entry (`01-architecture-overview.md` §2.2) when both its blocks exist; the end that is a real block is still checked like the wire command (an unknown port, a wrong direction or a fan-in skips it). Retained entries are not visible on the wire; the placeholder block itself is (`02-wire-protocol.md` §3.4).
- **Events**: loading reports the events those commands report (graph created, each block, edge, initial and graph port in file order, then `network:started` if `started`). Startup loads graphs before the listeners open (§1.4), so no client receives them; a later load (none exists yet) would broadcast them like the commands.

### 2.3 Storage layout, file naming, atomic writes

```
<datadir>/
  graphs/<encoded graph id>.json
  types/<encoded type name>.json     (composite / group block types, 03-block-types.md §5.1)
```

`<datadir>` is a plain directory on POSIX (default `<basedir>`) and the LittleFS mount on Zephyr (default `/lfs`). `graphs/` and `types/` share the same parent directory. The configuration and users files live in the configuration directory (§1.1).

**File naming**: users never see these files, so names only need to be safe and reversible:
- Graph ids and type names are limited to 64 bytes (`02-wire-protocol.md` §3.4.1).
- They are encoded by keeping the bytes `A–Z a–z 0–9 _ -` and writing every other byte as `%XX` (uppercase hex), then appending `.json`. For example, `math/MyBlock` → `math%2FMyBlock.json`, and a UUID is unchanged.
- The longest possible name (3 × 64 + 5 bytes) fits LittleFS's default 255-byte name limit.
- The id/name inside the file is authoritative; the file name is only an index.

**Atomic writes** — every write (graphs, types, configuration, users) uses the same procedure, so a power loss mid-write leaves either the old or the new file, never a torn one:
1. Write the complete content to `<name>.tmp` in the same directory.
2. Flush it to stable storage and close it (`fs_sync` on Zephyr; `fsync` on POSIX).
3. Rename `<name>.tmp` over `<name>`. The rename is atomic on LittleFS and on POSIX filesystems. On POSIX, also `fsync` the directory.
4. At startup, delete any leftover `*.tmp` (§1.4) in every directory the engine writes to: `<datadir>/graphs/`, `<datadir>/types/`, and the directories of the configuration and users files.

This procedure is the PAL operation `pal_storage_write` (`01-architecture-overview.md` §0.1), and step 4 is `pal_storage_remove_tmp`. The temporary file is the full file name plus `.tmp` (`x.json` → `x.json.tmp`, at most 201 bytes for an encoded name, within LittleFS's 255). On POSIX every system call is retried on `EINTR`, partial writes are continued, a failure before the rename removes the `.tmp` file and leaves the old file untouched, and files are created with mode `0600` (the same procedure writes the users file). A filesystem that cannot `fsync` a directory (`EINVAL`) is tolerated.

**Implementation decisions** (plan task 10, `src/app/file_names.h`, `src/app/graph_files.h`): decoding a file name accepts only what encoding produces (no `.json` suffix, a kept byte written as `%XX`, lowercase hex, a raw byte that needs escaping, or more than 64 decoded bytes are not graph files), so a decoded name always encodes back to the same file name. Paths are `<datadir>/graphs/<encoded id>.json` (a trailing `/` of `datadir` is ignored); a path that would not fit `PAL_PATH_MAX` with its `.tmp` suffix is refused. `<datadir>/graphs/` and `<datadir>/types/` are created if missing at startup (§1.4 step 2; one level, `datadir` itself must exist), and saving creates `graphs/` on demand. `run daemon` loads every regular file ending in `.json` in `<datadir>/graphs/` (so no `.tmp` leftover), in byte order of the file names, so graphs are created in the same order every boot; a file whose name is not the encoding of its graph's `id` is loaded with a warning (`network:persist` writes to the id's file). `run process` loads the given colon-separated files in order. Every file is tried; a failed one is logged and skipped (and then, for `run process`, the engine refuses to start: §1.4 step 7, decided in plan task 19).

**Type files** (decided, plan task 21; `src/app/type_files.h`): `types/<encoded name>.json` holds the type's authoring JSON in its canonical form (`03-block-types.md` §5.1), written atomically like every file; saving creates `types/` on demand. Registering a saved file again yields the same text. Loading is startup step 6 (§1.4). The model operations of the group commands (`02-wire-protocol.md` §3.4.2) pair with the files thus: a new type is saved under its name; a removed type's file is deleted (a missing file is fine, another failure is logged); a renamed type is saved under the new name and the old file deleted.

**Deleting**: `runtime:delete_graph` removes the graph's file (a graph that was never persisted has none; any other failure to remove it is logged as an error, and the deletion stands — the file would load again at the next boot); removing a group removes its type file (`02-wire-protocol.md` §3.2, §3.4.2). Renaming a graph changes only its `name`, never its `id`, so the file name stays the same.

## 3. Web server

The web server listens on `port` and serves only the frontend's static assets (HTML/JS/CSS bundle) from `webdir`. It does not handle the FBP protocol, which has its own WebSocket listener on `port + 1` (`02-wire-protocol.md` §0).
- Only `GET` (and `HEAD`, the same response without its body) is accepted. Unmatched paths without a file extension fall back to the SPA's entry document.
- The web server requires no authentication: the assets contain no secrets, and authentication happens on the WebSocket (`02-wire-protocol.md` §2).
- To save flash, assets may be stored pre-compressed: if `<file>.gz` exists and the request's `Accept-Encoding` includes `gzip`, serve it with `Content-Encoding: gzip`.

On the Zephyr build, assets live in LittleFS (`/lfs/web`), so the frontend can be updated without reflashing the firmware. Serving the bundle from flash carries a real storage-size budget — confirm the compressed bundle's size against the target MCU's flash budget during implementation.

Implementation decisions (plan task 13; `src/engine/web_server.h`, the request parser `src/protocol/http.h`, shared with the WebSocket upgrade of `02-wire-protocol.md` §0):
- **Server**: a small portable HTTP/1.1 server on the engine loop (`04-drivers.md` §6 option 1, `01-architecture-overview.md` §3.2.1), the same code on both build trees. `web_server_open_config` opens it from `host`, `port` and `webdir` in startup step 8 (§1.4); `web_server_close` after the loop returns.
- **Methods**: `GET` and `HEAD` (RFC 9110 requires both of a general-purpose server; `HEAD` costs nothing extra). Any other method is `405 Method Not Allowed` with `Allow: GET, HEAD`.
- **Request heads**: at most 8 KiB (`HTTP_HEAD_MAX`, room for a browser's cookies, which are shared by every port of the host) and 32 header fields (`HTTP_HEADERS_MAX`), both per-build overrides; parsed incrementally, so any split of the input works. A longer request line is `414`, a larger head or more fields `431`, a malformed head `400` (RFC 9112 syntax: single spaces in the request line, no whitespace before a field's colon, no line folding, no control bytes in values, exactly one `Host` for HTTP/1.1, `Content-Length` digits only and consistent, never with `Transfer-Encoding`), another HTTP major version `505`. Lines may end in a bare LF; empty lines before the request line are skipped. Only the origin form of the request target (`/path`) is accepted (`400` otherwise).
- **Paths**: the query is dropped and the path percent-decoded; a NUL, `/` or `\` written as `%XX`, a raw `\`, a control byte, a `.` or `..` segment, or an invalid escape is `400` (rejected, never resolved); a segment starting with `.` (a hidden file such as `.git`) is `404`; empty segments collapse; a path ending in `/` (`/` itself included) maps to `index.html` in that directory. The result is always below `webdir`. `webdir` itself is trusted: symbolic links inside it are followed (POSIX; LittleFS has none), since anyone who can place a link there can replace the frontend anyway.
- **SPA fallback**: a path that matches no regular file and whose last segment has no `.` (a client-side route such as `/graphs/x`, or a directory) is answered `200` with the entry document `index.html`; a missing path with an extension (`/app.js`) is a real `404`, so a script or stylesheet is never answered with HTML.
- **Pre-compressed assets**: when `Accept-Encoding` allows `gzip` — the field's token list parsed properly, `x-gzip` and `*` included, a weight `q=0` refusing, several fields forming one list, no field meaning no — `<file>.gz` is served if it exists, with `Content-Encoding: gzip` and the original file's `Content-Type`; otherwise `<file>`. An asset stored only as `<file>.gz` is therefore `404` to a client that does not take gzip.
- **Response headers**: `Content-Type` by extension (`html`/`htm`, `js`/`mjs` as `text/javascript`, `css`, `txt` with `charset=utf-8`; `json`/`map` `application/json`; `svg`, `png`, `jpg`/`jpeg`, `gif`, `webp`, `ico`, `woff`, `woff2`, `wasm`; anything else `application/octet-stream`); `Content-Length` always (no chunked encoding); `Vary: Accept-Encoding` on every file response; `Cache-Control: no-cache`, so a frontend update is picked up at once (there are no validators yet, so a revalidation downloads the asset again; an `ETag` would need a file modification time the PAL does not offer); `X-Content-Type-Options: nosniff`. No `Date` (no wall clock yet, `00-README.md` open question 11) and no `Server`. Error responses are small fixed `text/plain` bodies (`404 Not Found`).
- **Connections**: HTTP/1.1 keep-alive, one request at a time: reading pauses while a response is pending, and pipelined requests wait in the head buffer and are answered in order. A connection closes after a response to HTTP/1.0, to `Connection: close`, to a request with a body (it is never read), after a parse error (`400`, `414`, `431`, `505`), a timeout (`408`), `500` or `503` (`Connection: close` in the response). Before the close, the input already received (at most 64 KiB) is read and discarded, so the close sends FIN rather than a reset that could destroy the response in flight.
- **Streaming**: files are read in 4 KiB chunks through the PAL's streaming read (`01-architecture-overview.md` §0.1) into the connection's outgoing buffer as it drains (`on_drained`), never whole. A file that ends before the size announced in `Content-Length` aborts the connection. Reads are synchronous on the engine thread (local storage, one chunk per call).
- **Limits and timeouts** (per-build overrides): at most 16 connections (`WEB_MAX_CONNS`; a browser opens up to 6 per origin; a connection beyond it is closed unseen by the loop's hard cap — the WebSocket's `max_connections` is unrelated), an 8 KiB outgoing buffer each (`WEB_OUT_CAP`). Checked by a tick hook: 15 s idle (no byte of the next request after the accept or a response: closed), 10 s for a head from its first byte (`408`, then closed), 30 s without progress while a response is written out (aborted).
- **Errors**: a file that cannot be opened for lack of descriptors is `503`, any other storage failure `500`; both are logged at `warn`. One `info` line per response: peer address, method, path without the query, status, body bytes — never header fields.

## 4. Logging

Four severity levels, `fine < info < warn < error`, with a single verbosity threshold (`log.level`, §1.1): a message is emitted only if its level is at or above the configured threshold. Log lines are tagged with their source location (file/line) for traceability. Remote log mirroring relays log output to authenticated WebSocket clients as `network:output` (`fine`/`info`/`warn`) or `network:error` (`error`), per `02-wire-protocol.md` §3.3. It is enabled with `log.mirror` and is off by default. Secrets and credentials are never logged (`02-wire-protocol.md` §2.5 item 8).

- **Line format**: `<level> <file>:<line>: <message>` — the level name as in `log.level`, the source file's base name, no timestamp (`01-architecture-overview.md` §3.4 has no wall clock yet; a sink may add its own). A line is formatted into a fixed 256-byte buffer, so it holds at most 255 characters; a longer line is cut there with its last three characters replaced by `...`. No heap allocation per log call.
- **Sinks**: the portable core only formats; each line goes, with its level, to every registered sink (up to 4). The platform registers its console (stderr on POSIX, the Zephyr console later); the protocol layer registers the mirror when `log.mirror` is on and uses the level to choose `network:output` or `network:error`. With no sink registered, output is discarded.
- **Mirroring** (decided, plan task 17, `src/protocol/dispatcher.h`): with `log.mirror` on, the protocol layer registers its sink when it is created (startup step 8; a failure — no free sink slot — refuses startup) and removes it at shutdown. Each line passing the threshold is sent, exactly as formatted above (level, file and line included), to every connection whose session is live (`02-wire-protocol.md` §2.5 item 6): an `error` line as `network:error` `{"stack":"","message":"<line>"}`, any other as `network:output` `{"type":"message","message":"<line>"}`. A line that does not fit a connection's free outgoing space above the reserve kept for replies and events (`02-wire-protocol.md` §4.2 "Reserve"), or comes while a deferred burst waits for the buffer to drain (§1.2 there), is dropped for that connection, which stays open: mirroring is best effort and never closes a connection (unlike a graph event, `02-wire-protocol.md` §0). **No recursion**: a line logged while the protocol layer is sending a message (from inside the transport, e.g. the WebSocket server reporting a full buffer) or mirroring another line is not mirrored (the console still gets it unless it was logged from inside a sink, below). Log lines never contain secrets (`02-wire-protocol.md` §2.5 item 8), so mirroring needs no filter; they do carry user names and peer addresses (login lines), which every authenticated user may see.
- **Engine thread only**: logging is not locked (`01-architecture-overview.md` §3.2). IO workers and ISRs never log; they enqueue work and the engine-side handler logs. (Timers fire on the engine thread, `01-architecture-overview.md` §3.2 item 7.) A log call made from inside a sink is dropped.

## 5. Testing

Because the authorization component, the graph engine, the protocol dispatcher, and the IO provider are each separable modules behind interfaces (`01-architecture-overview.md` §0, §6; `02-wire-protocol.md` §2.5 item 10; `04-drivers.md` §0), unit tests can exercise protocol command handling against a fake authorizer, an in-memory graph, and the simulated IO provider, without real credential hashing or hardware access. Integration tests that exercise the real WebSocket/FBP protocol end-to-end should use the `02-wire-protocol.md` message catalog directly as the assertion basis: each documented request/response pair, and each refusal case in `02-wire-protocol.md` §3.4.1, is a concrete test case. Multi-client tests should check the command → event rule (`02-wire-protocol.md` §1.1): with two connections on the same graph, a command from one produces the identical event sequence on both, and a refused command produces no event on either.

Implementation (plan task 20): the end-to-end tests start the whole engine in-process (`engine_start` on ephemeral loopback ports, a temporary configuration, data and web directory, test users provisioned with a low iteration count) and drive it with real WebSocket clients on non-blocking sockets, running loop iterations while they wait — a wait is bounded by a number of iterations, never a sleep. The helpers are `tests/e2e.h`; the executables `test_e2e_catalog` (the message catalog of `02-wire-protocol.md` §1–§3, every refusal case of §3.4.1, the authentication errors of §2), `test_e2e_clients` (the command → event rule with byte-identical frames, scoping, the outgoing buffer, robustness) and `test_e2e_dataflow` (live values, a `timing/Interval` on the real clock, persistence across a restart). "Nothing else arrived" is checked with a barrier: a request whose reply must be the next message on that connection, since the engine sends each connection its messages in order.
