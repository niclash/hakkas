# 01 — Core Architecture: Graph Engine, Concurrency Model, Module Map

## 0. Platform Abstraction Layer (PAL)

The core engine — the graph/block model, protocol dispatch, and persistence JSON handling — is portable, platform-independent C. No Zephyr headers, no POSIX headers, and no direct hardware access appear anywhere in the graph engine, block type, protocol, or persistence code. All of that code calls only a small set of PAL functions, implemented once per target:

- **`platform/zephyr/`** — the MCU implementation: Zephyr sockets (`zsock_*`) for networking, with `zsock_poll`'s timeout as the engine's only timing primitive (timers are deadlines kept by the portable core, §3.2 item 7), `k_work` for deferred work such as the hardware-polling worker, one Zephyr thread (or the system work queue) as the engine thread, Zephyr's filesystem subsystem over LittleFS for persistence, and Zephyr's device driver subsystem for hardware access (`04-drivers.md`).
- **`platform/posix/`** — the Raspberry Pi / Linux / x86_64-development implementation: POSIX sockets, `poll()` with a timeout as the only timing primitive (no `timerfd`, §3.2 item 7), a single process thread, a POSIX filesystem directory tree for persistence, and a **simulated IO provider** so a complete development system runs on a desktop with no hardware.

The PAL surface is small and deliberate: open/close/read/write/poll (with a timeout) for sockets, a monotonic millisecond clock, read/write/rename/remove/exists/list for storage (plus a streaming read for files too large for one buffer), a random-bytes source (for UUIDs and session secrets), a console sink for log lines (`05-app-lifecycle-persistence.md` §4), an **IO-provider interface** (enumerate channels, write a channel, deliver channel events — `04-drivers.md`), and one function to enqueue work onto the engine's queue from a different execution context (needed because the hardware-polling worker in `04-drivers.md` §1 runs outside the engine's own thread and must hand work off rather than call into the engine directly — see §3.2.1; decided in §0.2). There are no PAL timers (decided, plan task 8): every timer is a deadline kept by the portable core and fired by the engine loop itself (§3.2 item 7), so no timer callback ever runs in another context. **Only a small, isolated number of files contain platform-specific code at all** — everything else, including every block type and the entire protocol layer, is platform-agnostic and compiles unchanged against either PAL implementation.

### 0.1 PAL clock, random source and storage

The interface is `src/platform/pal.h`; every call returns `PAL_OK` (0) or a negative `pal_err` code (`PAL_ERR_NOT_FOUND`, `PAL_ERR_TOO_BIG`, `PAL_ERR_NAME_TOO_LONG`, `PAL_ERR_NO_SPACE`, `PAL_ERR_DENIED`, `PAL_ERR_IO`, ...). Decisions:
- **Initialization**: `pal_init()` initializes clock, random source and storage (`05-app-lifecycle-persistence.md` §1.4 step 2). The platform calls it once, before the configuration is read in step 1, since that read goes through the PAL (decided, plan task 19).
- **Clock**: `pal_uptime_ms()` is engine uptime (§3.4) — monotonic `uint64_t` milliseconds since the engine started: since boot on Zephyr, since `pal_init()` on POSIX (`CLOCK_MONOTONIC`, so not since host boot).
- **Random**: `pal_random_bytes()` fills a buffer from the platform CSPRNG (POSIX: `getrandom()`); on failure it reports an error and never falls back to a weaker source.
- **Paths**: storage calls take platform paths used as given, built by the core by joining a configured directory (`datadir`, `confdir`, … — `05-app-lifecycle-persistence.md` §1.1) with relative names using `/`. The PAL resolves no root of its own (`/lfs/graphs/x.json` on Zephyr, `<basedir>/graphs/x.json` on POSIX). A path, including the `.tmp` suffix of an atomic write, must fit `PAL_PATH_MAX` (256 bytes with the NUL, overridable per build).
- **Memory**: storage functions never allocate on the heap; file content is read into and written from caller-provided buffers. `pal_storage_read` fails with `PAL_ERR_TOO_BIG` (reporting the file size) if the buffer is too small; `pal_storage_stat` gives the size beforehand.
- **Operations**: `stat`/`exists`, `read`, `write`, `rename` (replaces the target), `remove` (files only), `mkdir` (one level, succeeds if the directory exists — for `graphs/` and `types/`), `list` (a callback per entry, no list built in memory; `.`/`..` skipped; regular files and directories only), and `remove_tmp` (deletes the `*.tmp` leftovers in one directory, not recursive).
- **Writes are always atomic**: `pal_storage_write` is the procedure of `05-app-lifecycle-persistence.md` §2.3; there is no non-atomic write. Renames and removes are made durable as well (POSIX: the directory is `fsync`ed).
- **Streaming reads** (decided, plan task 13): a file too large for one buffer — a web asset, `05-app-lifecycle-persistence.md` §3 — is read in chunks: `pal_file_open` (read-only, regular files only, reporting the size), `pal_file_read` (sequential, a count of 0 at the end) and `pal_file_close`. A file handle is an `int` on both ports: a descriptor on POSIX (opened `O_NONBLOCK`, so a special file such as a FIFO never blocks the open; it is refused), an index into a small fixed table of open files on Zephyr, so no heap either. Running out of descriptors or table slots is `PAL_ERR_UNAVAILABLE` (on POSIX also for every storage call that runs out of descriptors). There is no streaming write: every write stays atomic.

### 0.2 PAL sockets, poll and cross-context enqueue

Decided in plan task 12 (`src/platform/pal.h`; POSIX: `src/platform/posix/socket.c`, `wakeup.c`, `signals.c`):
- **Sockets**: a small non-blocking TCP server API — `pal_socket_listen` (host, port, backlog; port 0 picks an ephemeral port, `pal_socket_local_port` tells which), `pal_socket_accept` (with the peer's address), `pal_socket_read`, `pal_socket_write` (may write part of the data), `pal_socket_close` — and `pal_poll` over a set of sockets with a millisecond timeout, reporting readable/writable/error per socket. A socket is an `int` descriptor on both ports. Every socket is non-blocking: a call that cannot proceed returns `PAL_ERR_WOULD_BLOCK`; the end of stream or a reset is `PAL_ERR_CLOSED`; a taken port is `PAL_ERR_ADDR_IN_USE`; lack of descriptors or buffers is `PAL_ERR_UNAVAILABLE`.
- **Addresses**: `host` is a numeric IPv4 or IPv6 literal; host names are not resolved (no DNS at startup). IPv6 is supported: listening on `"::"` also accepts IPv4 where the system allows it (`IPV6_V6ONLY` off). A peer address is text in its usual form; an IPv4 peer of an IPv6 listener is shown as plain IPv4, so one client has one address for logging and rate limiting (`02-wire-protocol.md` §2.5 items 7–8).
- **TLS** is not part of the PAL socket API: an optional TLS layer (`02-wire-protocol.md` §2.5 item 9) would wrap a connection's reads and writes in the event loop.
- **Cross-context enqueue**: `pal_handoff_push` moves one work entry (§3.2; in practice an IO event, `04-drivers.md` §0) into a bounded FIFO in the PAL, of `PAL_HANDOFF_CAPACITY` entries (default 64, a per-build override), and wakes `pal_poll`; the engine loop takes the entries (`pal_handoff_take`) into the work queue on the engine thread, in push order. The handoff's lock is the only lock in the system, and it lives in the PAL. Any context may push, but not an interrupt handler (the push may wait briefly on the lock). The pushed value must be one no other context holds a reference to, since `Linkable` references are not thread-safe. **When the handoff is full**, the oldest entry is dropped (its value released) and counted, like the work queue (§3.2 item 9); the engine loop logs a rate-limited warning of its own (same 10 s interval). The handoff and its wakeup exist between `pal_loop_open` and `pal_loop_close` (the engine loop's init and deinit); a push outside that is refused and its value released.
- **Stop request**: `pal_request_stop` sets a flag the engine loop checks and wakes `pal_poll`; any context may call it, on POSIX also a signal handler. A request made before the loop runs stops it at once; `pal_loop_close` clears it.
- **POSIX**: plain BSD sockets, non-blocking and close-on-exec (`SOCK_NONBLOCK`/`SOCK_CLOEXEC`, `accept4`), `SO_REUSEADDR` on listeners (a restart can bind at once), `TCP_NODELAY` on connections (small protocol messages; latency matters), `MSG_NOSIGNAL` on every send rather than ignoring `SIGPIPE` process-wide, every call retried on `EINTR`. `pal_poll` is `poll()`, which always also polls the wakeup: one `eventfd` (Linux-specific, like `getrandom`; a self-pipe would need two descriptors), written by a push only when no wakeup is pending yet, so a burst of pushes costs one write. The handoff is a mutex-protected ring. `SIGINT` and `SIGTERM` stop the loop: their handlers (installed without `SA_RESTART` by `posix_stop_signals_install`, `src/platform/posix/signals.h`) only call `pal_request_stop`, which is async-signal-safe (a lock-free atomic flag plus the `eventfd` write).

## 1. What the system does

Users wire "blocks" — components with named, typed input/output ports — into a dataflow graph. There is no separate edit/run mode: the graph is always live, and any structural change (add/remove/connect/rename) or value change takes effect immediately, mid-execution, exactly like rewiring electronics while powered. Each block recomputes its outputs whenever its inputs change (or, for timer-driven block types, on a schedule), and every output change propagates to every connected downstream input. A WebSocket protocol (`02-wire-protocol.md`) — a dialect of the FBP network protocol — lets a browser-based editor observe and mutate the running graph in real time.

## 2. Core data model

### 2.1 Value type — `Linkable`

Every port holds exactly one dynamically-typed value: a string, a signed 64-bit integer, a double, a boolean, a physical-unit-tagged `Metric` value, or "unset." There is no array/list value type. Type name strings used in port descriptors are `"bool"`, `"number"`, `"string"`. (`"link"` appears in the frontend's type list for inter-graph port placeholders; it is reserved and never produced by this implementation.) A `Metric` travels through `"number"` ports.

**`Metric`** — *provisional; this may be reworked or dropped once tried in practice (`00-README.md`, open question 9)*: a tagged physical-unit value — a magnitude (double) plus a unit, organized into categories (acceleration, angle, area, current, density, distance, energy, flow, force, frequency, gravity, humidity, mass, periodicity, power, pressure, ratio, resistance, temperature, velocity, voltage, volume). Parsing a metric from text splits on the first space into `(value, unit)` and matches the unit against per-category unit tables (not yet defined). **C model**: `struct { double value; const char *unit; enum metric_category category; }`.

Intent:
- **Origin**: IO modules produce `Metric` values (a temperature, a voltage, …), not bare numbers (`04-drivers.md`).
- **Mapping**: the user can re-map a measured metric into what it physically represents — e.g. a sensor that measures 0–10 V is mapped to a level sensor reading 0–300 mm (`distance`). Where this mapping lives (a channel setting or a dedicated mapping block type) is not decided.
- **Arithmetic preserves units**: adding/subtracting/comparing metrics of the same category preserves the category (two temperatures add to a temperature). Combining mismatched categories in an additive operation sets the block's **error flag** (a per-block-instance boolean; how it is shown on the wire is not yet specified) and the numeric result is still computed from the magnitudes. Multiplication/division follow physical dimensions where a known relation exists (mass × acceleration → force); otherwise the result is a plain number.
- Mixing a metric with a plain number is not yet specified.

**Type conversions**, used throughout block computation:
```
to_f64(v):  f64→v; i64→(double)v; metric→v.value; bool→1.0:0.0; string→parse as f64, else 0; unset→0.0
to_i64(v):  f64→(int64_t)v; i64→v; metric→(int64_t)v.value; bool→1:0; string→parse as i64, else 0; unset→0
to_u64(v):  f64→(uint64_t)v; i64→(uint64_t)v; metric→(uint64_t)v.value; bool→1:0; string→parse as u64, else 0; unset→0
to_bool(v): bool→v; f64→v!=0.0; metric→v.value!=0.0; i64→v!=0; string→(v=="true") [exact match only]; unset→false
default_value(typename): "bool"→false; "number"→0.0; "string"→""; else→0.0
```
**String parsing** ("parse as f64 / i64 / u64" above) is strict: the whole string must match, with no surrounding whitespace and no trailing characters, otherwise the result is the `0` of the table (so `"12abc"`, `" 12"` and `""` all give `0`).
- f64: `[+-]? (digits [. digits*] | . digits) [(e|E) [+-]? digits]`, or exactly `NaN`, `Infinity`, `+Infinity`, `-Infinity`. Hexadecimal and the C library's `inf`/`nan` spellings are not accepted. Decimal text beyond the double range gives ±Infinity.
- i64: `[+-]? digits`, within the `int64_t` range; u64: `[+]? digits`, within the `uint64_t` range. Integer parsing does not go through f64: `"12.5"` and `"1e3"` are not integers and give `0`, as does an out-of-range integer string.

**Double → integer** (NaN, ±Infinity, out-of-range — decided, `00-README.md` open question 8): `to_i64`/`to_u64` of a double (an f64, a `Metric` magnitude) **saturate**. NaN → `0`; a value at or beyond the target type's upper bound → `INT64_MAX`/`UINT64_MAX` (+Infinity included); below the lower bound → `INT64_MIN`/`0` (−Infinity and every negative value ≤ −1 for `to_u64`); everything else truncates toward zero as the C cast does. This costs a NaN test and two comparisons, is well-defined C (a plain cast of such a value is undefined behavior), and matches what common FPUs' conversion instructions do. Note the asymmetry it leaves: `to_u64` of the f64 `-1.0` is `0`, while `to_u64` of the i64 `-1` is the modular C cast, `UINT64_MAX`.

**Stringifying** a value for display/wire transport uses each type's natural string representation; a value with no natural string form — "unset" — renders as `"<not stringable>"`. The forms:
- string: as-is; i64: decimal; bool: `"true"`/`"false"` (so `to_bool` reads it back);
- f64: the shortest of C's `"%.15g"`, `"%.16g"`, `"%.17g"` that parses back to the identical double, so every finite double round-trips through text while common values stay short (`0.1`, `5`, `1e+20`); non-finite values are `NaN`, `Infinity`, `-Infinity` (JavaScript's spellings, also accepted by the f64 parser);
- `Metric`: `"<value as f64> <unit>"`, the form a `"number"` port parses back into a `Metric` (`02-wire-protocol.md` §3.4).

Number text is always in the C locale (`.` decimal point).

Until unit tables exist (open question 9), a `Metric` parsed from text keeps its unit string verbatim and gets the category **unclassified**, an extra category value besides the list above.

There is no "error" behavior in value computation — as in electronics, every operation has well-defined limits and a well-defined result when they are exceeded (e.g. IEEE-754 `±Infinity`/`NaN` for division by zero). Blocks never reject a value.

Port descriptors carry: `name`, `description`, `type`, `default` (the value the input holds when nothing is wired to it; falls back to `default_value(type)` if the block type doesn't specify one), `addressable` (bool — reserved metadata; nothing in the runtime currently indexes by address), and, for ports belonging to a composite block type (`03-block-types.md` §5), a `target`/`source` reference into the inner block graph.

### 2.2 Entities and ownership

```
Engine
 └─ Graphs  (engine-wide registry)
     └─ Graph  (one dataflow network, a.k.a. "process"; has an id, name, description, icon)
         ├─ Block[]        (named instances of a block type)
         │    ├─ Input[]   (named, typed, holds current value; fed by at most ONE source: an upstream output OR a literal "initial")
         │    └─ Output[]  (named, typed, holds current + last-propagated value + list of links to downstream inputs)
         ├─ Port[] (inports)   — a graph-level named input mapped to one inner block's input
         └─ Port[] (outports)  — a graph-level named output mapped to one inner block's output
```

- **Engine**: always running while the system is up. It hosts any number of graphs simultaneously; graphs are started and stopped individually, the engine never is.
- **`Graphs`**: owns the `id → Graph` map, the uptime accounting of every graph (computed from engine time, no timer — implementation decisions below), and the list of **subscribers** (§4) that every structural/lifecycle event is broadcast to. Also owns link-value subscription plumbing (`subscribe_links`/`unsubscribe_links`), forwarded down to the target `Graph`.
- **`Graph`**: owns its blocks (keyed by instance name) and its exported ports (inports/outports, keyed by exported name). Tracks `started`/`running`/`debug`/`uptime`/`time_started` (`running` mirrors `started`; `debug` is always `false` — there is no debug mode). Every mutating operation (`create_block`, `connect`, `disconnect`, `remove_block`, `rename_block`, `add_inport`, etc.) performs the mutation **and** reports it to `Graphs`, which fans it out to every subscriber — this is the sole mechanism driving the wire protocol's broadcast messages (`graph:addnode`, `graph:addedge`, etc. — `02-wire-protocol.md` §3.4).
- **Started vs. stopped graph**: a stopped graph keeps its full structure and its inputs keep accepting values (structural edits and initials still apply), but **no events propagate**: no compute steps run, no outputs are pushed downstream, and its timers are cancelled. Starting a graph runs every block's compute step once with its current inputs and pushes every output downstream unconditionally (bypassing the change threshold, §3.3), then resumes normal propagation. A block added to a started graph is started immediately.
- **`Block`**: the uniform contract every block type implements — `update(input, value)`, `get_input`/`get_output`, `set_initial`/`remove_initial`, `connect`/`disconnect_edge`/`disconnect_block`, `rename`/`rename_of`, `change(metadata)`, `start`/`stop`/`destroy`, `refresh`, `describe`, `subscribe_link`/`unsubscribe_link`. **This contract is implemented once, generically** — see §2.3 — not once per block type.
- **`Input`**: holds `value`, its single source (none, one upstream link, or one literal initial), and a list of **live-value subscriptions** used by the `network:edges` wire feature (`02-wire-protocol.md` §4.2) to stream a value to a specific client.
  - **No fan-in**: an input is connected to at most one source. Connecting an output to an already-fed input, or adding an initial to an input fed by an edge, is invalid (`02-wire-protocol.md` §3.4.1). Adding an initial to an input that already has one replaces the literal value.
  - **Initials** (FBP term — see `fbp-protocol.html`): a literal value wired to an input in place of an upstream output, like tying a pin to a fixed voltage. Adding an initial delivers its value to the input immediately (it propagates through the graph like any other input change, if the graph is started). Initials must be wired explicitly; there is no implicit "stored default" per input.
  - **Severing**: when an input's source is removed (edge removed, initial removed, upstream block removed), the input immediately reverts to its port's `default` value (§2.1), exactly as an unconnected pin in electronics falls to its defined level, and that change propagates. Any queued, not-yet-delivered values from the severed link are dropped (§3.2).
- **`Output`**: holds `value`, `last_propagated` (the value most recently pushed downstream, used by the change threshold, §3.3), and a list of links — each a `(destination_block, destination_input_name)` pair. An output may fan out to any number of inputs. Setting an output's value (`output_set`, §3.2) is **the single propagation primitive the entire dataflow engine is built on.** A newly connected link immediately receives the output's current `last_propagated` value — wiring a connection delivers the signal already present on it.
- **`Port`** (inport/outport): a graph-level named port mapped to one inner block's input/output. Its purpose is to define the external interface the graph has when it is used as a group/composite block type (`03-block-types.md` §5; creating a group from a selection exposes the graph-level ports that target selected nodes, §5.2). In a top-level graph that isn't used as a composite, inports/outports have no dataflow effect — they are metadata. A port refers to its inner block itself, not to the block's name: renaming the block carries the port along (no port event), and removing the block removes every port mapped to it, reported after the block's edges and initials and before the block (decided, plan task 7; `02-wire-protocol.md` §3.4). Using them to link processes together is open (`00-README.md`, open question 13).

**Implementation decisions** (plan task 6, `src/graphs/runtime.h`, `src/graphs/graph.h`):
- **Runtime context**: one `Runtime` holds the engine-wide pieces — the work queue (§3.2), the block slot table that resolves block handles, the block timers (§3.2 item 7), the engine-wide default change threshold (§3.3) and the current engine time handed to `compute`. It never reads a clock: the engine loop sets the time (from `pal_uptime_ms()`) before draining, so tests control time.
- **Memory**: the work queue is a fixed array (§3.2 item 9). Blocks, graphs, names, value arrays, link lists and state blobs are heap-allocated, sized exactly when a block is created or a link added; nothing is allocated while values propagate, except strings (§2.1). The slot table is one heap array that grows by doubling and reuses freed slots. An allocation failure refuses the operation that needed it, with no change.
- **Blocks** keep creation order in their graph (the order `graph:connect` snapshots and start use). An input's source is none, one edge or one initial, with its source generation (§3.2); an output holds its links in connection order. Before a block's first start, an output's `last_propagated` is its port default. Node metadata holds `x`/`y` (default 50) and the optional `change_threshold` override.
- **Opaque metadata** (decided, plan task 10, `src/graphs/graph_json.h`): a node's other metadata keys and an edge's metadata are never interpreted. Each is kept as one heap string of compact JSON object text, sized exactly (no parsed JSON tree stays alive): the node's on the block, the edge's on its destination input, which has at most one edge. A node without other keys or an edge without metadata holds none. The text is printed with exact numbers (§6, cJSON), so it is written back unchanged in value; it is parsed only to save the graph, to merge a `changenode` patch (`02-wire-protocol.md` §3.4) or to send it on the wire. Removing an edge drops its metadata.
- **Placeholder blocks** (decided, plan task 10; `05-app-lifecycle-persistence.md` §2.2): a block whose type is `NULL`, created only by graph-file loading for an unregistered component. It keeps the component name, has no ports and no compute, and otherwise behaves like any block (it is reported, renamed, changed, started, removed). The file's connections and graph ports that reference a placeholder cannot be live links; the graph keeps them as **retained entries** that point to their blocks (so they follow a rename), are written back on save, appear in no event and no `graph:connect` snapshot, and are dropped silently with either of their blocks. A retained connection is checked like the wire command on its real end (port and direction) and counts as the source of a real input, so the model never holds a fan-in: a retained connection into an input that already has a source is refused, and a later live edge or initial to that input, or a live graph port taking a retained port's name, replaces the retained entry (it is dropped silently).
- **Value delivery by a structural operation** — an initial added or replaced, a severed input reverting to its default, a new edge delivering `last_propagated` — goes straight through the target block's `update` (§3.1: an operation on that block, not a call from another block), exactly the code the drain loop runs for a queued input update: store, live-value subscriptions, compute step if started. The input therefore never shows a stale value once the operation returns, a severed input's revert cannot be lost to queue overflow, and only the downstream effects are queued. Values from an upstream output always travel through the queue (§3.2).
- **Change reporting**: every applied structural change (block added/removed/renamed/changed, edge added/removed, initial added/removed, and from plan task 7 graph port added/removed/renamed) is reported to one runtime-wide observer, which the `Graphs` registry (plan task 7) fans out (§4); each report follows its structural change and precedes the value delivery it causes. Removing a block reports every removed edge and initial (its inputs in port order, then its outputs' links in port and connection order) and then the block (`02-wire-protocol.md` §1.1). Start and stop are not reported by the graph; `Graphs` emits `network:started`/`stopped`. Destroying a whole graph reports nothing.
- **Watches**: an input's live-value subscriptions are callbacks registered on the input; one fires immediately with the current value when registered, then after every update, and is detached (with a notification) when its block is removed.

**Implementation decisions** (plan task 7, `src/graphs/graphs.h`):
- **Registry**: `Graphs` keeps its graphs in creation order (the order of `graph:list` and the status broadcasts) and looks them up by id. A graph's id, name, description, icon, ports and lifecycle times are fields of the `Graph`; the registry manages them. It is the runtime's single observer and forwards every structural event into its subscriber fan-out (§4). Block types are resolved through a function the engine passes in (`block_types_get`), so `graphs/` does not depend on `blocktypes/` (§2.3); likewise the UUID random source (`pal_random_bytes`) is passed in, so the core links no PAL symbol and tests can substitute one.
- **New graph ids**: a random UUID version 4 (RFC 9562), lowercase text form; a drawn id that is already taken is redrawn a few times, then refused as `Graph exists`.
- **Uptime is computed, not counted**: a graph records the engine time when it starts (`time_started`); its uptime is the runtime's current engine time minus that, 0 when stopped. There is no once-per-second uptime timer — it would only approximate the same number. The engine loop sets the runtime's time from `pal_uptime_ms()` before it dispatches commands as well as before draining (§3.4). On stop the run's duration is kept, so `network:stopped` reports the start and duration of the run that ended (`02-wire-protocol.md` §3.3). Events carry milliseconds; the wire floors uptime to whole seconds.
- **Delete**: deleting a started graph stops it first and reports the stop (`network:stopped`) before the deletion (`02-wire-protocol.md` §1.1, compound effects); the graph's blocks go without events. Removing the persisted file is graph persistence's part: `runtime:delete_graph` goes through `graph_files_delete` (`src/app/graph_files.h`, plan task 10), which deletes the graph and then its file.

**Metadata is for the user interface only** (decided, `00-README.md` open question 5): node and edge metadata support UI interactions (positions, routing, …) and must never drive the live function of a block. Anything that affects behavior is an input port. *Known conflict*: the per-block `change_threshold` override is currently kept in node metadata (§3.3); resolving it is part of open question 7.

### 2.3 One generic block runtime, not one implementation per block type

Almost all of a block type's logic is identical event-handling plumbing — react to an input changing, recompute, propagate the output. The only real per-type difference is *which function* does the computing. The engine should reflect that directly: implement the entire `Block` contract **once**, as shared generic code, driven by a per-block-type data record:

```
struct BlockTypeDef {
    const char *name, *icon, *description;
    InputDescriptor  inputs[N];
    OutputDescriptor outputs[M];
    bool             compute_on_input; // run compute whenever an input changes
    TimerMode        timer;            // TIMER_NONE | TIMER_PERIODIC | TIMER_SCHEDULED
    uint32_t         period_ms;        // TIMER_PERIODIC only: default period (a block may expose an input that overrides it)
    ComputeFn        compute;          // int64_t compute(BlockCtx *ctx) — see below
    size_t           state_size;       // 0 for stateless types; >0 reserves a per-instance opaque blob
    double           change_threshold; // type default for §3.3; NAN = use the engine-wide default
};

struct BlockCtx {
    const Linkable *inputs;  Linkable *outputs;  void *state;
    uint64_t now_ms;         // engine monotonic time (§3.4)
    Reason   reason;         // START | INPUT | TIMER | STOP
    int      changed_input;  // index of the input that changed, when reason == INPUT
    bool    *error;          // the block's error flag (§2.1, Metric)
};
```

**C representation** (decided, plan task 5): `BlockTypeDef`, `PortDescriptor`, `BlockCtx`, `TimerMode` and `Reason` live in `src/graphs/block_type.h`, the contract between the generic runtime (`graphs/`) and the block types (`blocktypes/`), so that `blocktypes/` depends on `graphs/` and never the reverse; the runtime works on a `const BlockTypeDef *` and never consults the registry. Inputs and outputs share one `PortDescriptor` (name, description, type, default as a `Linkable`, `addressable`, and `inner`: the composite port's `"InnerBlock.port"` target/source, `NULL` for built-ins), held as a pointer plus a count per direction. An output's `default` is its value before its first compute. Built-in definitions are static const data: port defaults are scalars or the static empty string, which own nothing. A `subgraph` flag and a pointer to the composite definition (`CompositeDef`: the inner blocks with their resolved types, the internal edges and initials, and per exposed port the inner `(block, port)` it maps to, all by index — decided, plan task 21) mark composite types (`03-block-types.md` §5); their `compute` is `NULL`. `compute` writes an output by replacing the block-owned value in `ctx.outputs` (an output it doesn't write keeps its value); `changed_input` is `-1` unless `reason == INPUT`; `error` is never `NULL`.

**Registry** (decided, plan task 5): `block_types_get(name)` (§3.5) looks types up by exact name in a fixed table of `HAKKAS_BLOCK_TYPES_MAX` entries (default 128, a per-build compile-time override), kept in registration order for `component:list` (`02-wire-protocol.md` §3.5). The registry doesn't own the definitions. Registering a name that is already registered is refused; unregistering keeps the order of the rest; a rename (`02-wire-protocol.md` §3.4.2) is unregister plus register, which moves the type to the end. The built-ins are registered at startup in the order of the `03-block-types.md` §3 table.

`compute` returns, for `TIMER_SCHEDULED` types only, the delay in milliseconds until it wants to be called again with `reason = TIMER` (a negative value means "no timer armed"); every call re-arms or cancels the block's single one-shot timer, except the `STOP` call, whose return value is ignored (decided, plan task 8: a stopped block has no timer, §3.2 timer decisions). For other timer modes the return value is ignored.

A block *instance* is this type-definition pointer plus an array of current input/output values, its own optional change-threshold override (§3.3), and, when `state_size > 0`, a per-instance state blob the `compute` function reads and writes across invocations. This single mechanism covers every block type in `03-block-types.md`:
- **Event-driven** (`compute_on_input = true`, `TIMER_NONE`): the arithmetic/comparison blocks, the linear-transform block. `state_size = 0`, `compute` is a pure function of its inputs.
- **Scheduled** (`TIMER_SCHEDULED`, usually also `compute_on_input`): the block decides when it next runs — the pulse/PWM generator (`03-block-types.md` §3.1) arms its timer for the next edge; schedule blocks (`03-block-types.md` §6.2) arm for the next schedule boundary.
- **Cyclic** (`TIMER_PERIODIC`, usually also `compute_on_input`): the block runs at a fixed sample period and additionally reacts to input changes — the PID regulator (`03-block-types.md` §6.1).

The shared generic code implements the propagation chain in §3 exactly once, calling `compute(...)` at the right moments; it never needs to know which concrete block type it's running. The exact moments are specified in `03-block-types.md` §2.

### 2.4 Naming convention

A fully-qualified port reference is the string `"<block-instance-name>.<port-name>"`, parsed by splitting on the **last** `.` — never the first, since instance names are user-chosen and may themselves contain dots. Use one single, correct implementation of this parse rule everywhere a `"block.port"` string needs to be split; there is no scenario where a different splitting rule is correct.

## 3. Propagation semantics

### 3.1 Concurrency model

Each block is an independent, single-threaded unit of state: its operations (`update`, `refresh`, `connect`, ...) are processed one at a time, to completion, never overlapping with another operation on the *same* block. A call from one block into another (e.g. an output's `set()` calling a downstream block's `update()`) is asynchronous: it enqueues work for the receiving block and returns immediately, rather than calling into it directly. Within one block, a `refresh()` triggered from inside `update()` is effectively "the next thing this block does to itself," so a single block's own chain (`update` → set input → `refresh` → compute → set output) looks synchronous from that block's perspective — but anything that crosses to another block is always queued work, never a nested call.

### 3.2 The engine loop

Model the whole engine as **one thread with one global FIFO work queue**. Queue entries are typed:
- **input update** `(target_block, input_port, value)` — produced by `output_set`. A value delivered by a structural command (an initial, severing, a new edge — §2.2) is not queued: it updates the target input directly, and only its downstream effects are queued (implementation decisions, §2.2);
- **timer expiry** `(target_block, timer generation)` — produced by the runtime's timer service when the block's deadline has passed (item 7);
- **IO event** `(channel, value)` — produced by the hardware/simulated IO layer (`04-drivers.md`).

Entries reference blocks by a **handle** (slot index + generation counter), never a raw pointer, so an entry whose block has since been removed is recognized as stale and discarded. When a link is removed, queued input updates that were produced by that link are dropped as well (e.g. each input carries a source-generation counter that increments whenever its source changes; an input update carries the generation it was sent under and is discarded on mismatch).

1. `output_set(output, value)`: store the new value on the output; if it differs from `last_propagated` by the change threshold (§3.3), set `last_propagated` and, for each downstream link, push an input update `(link.block, link.input, value)` onto the global queue — never call into the downstream block directly.
2. A drain loop pops the queue head, dispatches it (for an input update: `block_update(block, input, value)`, which sets the input and — if the block's graph is started and its type has `compute_on_input` — runs its compute-and-propagate step, which may push more work onto the same queue), and repeats until the queue is empty.
3. This gives **FIFO ordering per block** (a block always processes its queued updates in the order they arrived) and **breadth-first propagation overall** (a block's own refresh completes and re-queues its downstream effects before any of *those* effects are processed) — without needing locks or a scheduler.
4. **Cycles do not deadlock**: a cycle in the graph just keeps enqueuing and draining. Don't add cycle detection beyond this — an unconditional feedback loop will consume CPU indefinitely, which is a property of the graph the user built, not something the engine guards against.
5. There is **no global ordering guarantee stronger than "FIFO per block, breadth-first overall."** Two independent chains' relative interleaving is not specified further than that; don't invent a stronger guarantee than this.
6. **Input changes trigger compute only for `compute_on_input` types** — other types store the new value and use it at their next timer-driven compute. The exact `start`/`stop`/`destroy`/`connect`/`subscribe_link` behavior of the generic runtime is specified in `03-block-types.md` §2.
7. **Timers** (decided, plan task 8): the engine needs timers for scheduled/cyclic block types (graph uptime is computed from engine time and needs no timer, §2.2). They live entirely in the portable core: each block of a timer type has one timer, a **deadline** (an absolute engine time, §3.4) in a min-heap ordered by due time. There is no per-timer PAL or OS timer and nothing fires from another execution context: each iteration, the engine loop queues a timer-expiry entry for every block whose deadline has passed, then waits for socket readiness at most until the earliest remaining deadline (the poll timeout, §3.2.1). The expiry is dispatched from the same global queue as every other entry, keeping all propagation on one consistent code path. Other engine timeouts — the login nonce and session expiry of `02-wire-protocol.md` §2.5 — need no PAL timer either: they are checked against the clock when the loop wakes or kept as deadlines in a heap of their own, and the loop's poll timeout is the earliest of all of them.
8. **Socket I/O and protocol dispatch** integrate with this same loop (socket readability and timer expiry checked from the same place) rather than running on separate threads — the whole system is single-threaded and deterministic, with no synchronization primitives needed in the core engine.
9. **Queue capacity and overflow**: the queue is a fixed-capacity ring buffer (no unbounded growth on an MCU). Its capacity is fixed at build time: a default of 1024 entries, overridable per build. Deriving the capacity from the total number of wires (edges + initials) is deferred until real graph sizes are known (`00-README.md`, open question 10). If the queue is nevertheless full, the **oldest** entry is dropped to make room; the engine counts drops and logs a rate-limited `warn`.

Implementation decisions (`src/graphs/work_queue.h`):
- **Capacity override**: the capacity is the compile-time constant `HAKKAS_QUEUE_CAPACITY` (default 1024), set from CMake with `-DHAKKAS_QUEUE_CAPACITY=<n>` or, in a port's own build, by defining the macro. The ring is an array inside the queue struct the engine owns; nothing is heap-allocated.
- **Handles and generations**: a block handle is a 32-bit slot index plus the slot's 32-bit generation, which is incremented whenever the block in that slot is destroyed; an entry whose handle generation differs from its slot's (or whose slot is free) is stale. Each input's 32-bit source generation is incremented whenever its source changes (edge or initial added, replaced or removed, upstream block removed); an input update carries the value seen when it was enqueued. A timer expiry carries the block's timer generation, incremented whenever its timer is re-armed or cancelled (including on stop/destroy; a periodic timer's own continuation keeps it — timer decisions below), so an expiry of a superseded or cancelled timer is stale. The queue only carries these numbers; the dispatcher compares them and discards stale entries, so there is no "remove entries of block X" operation.
- **IO channel ids** are 32-bit integers in queue entries (provisional, like the whole IO hookup, `04-drivers.md`).
- **Values**: each entry owns a reference to its `Linkable` value (§2.1); dropping or discarding an entry releases it.
- **Overflow warning**: the queue only counts drops. The engine loop calls a report function once per iteration with the current uptime; it logs one `warn` line with the number of drops since the previous warning and the total, at most once per 10 s (`WORK_QUEUE_DROP_REPORT_INTERVAL_MS`). The first drops after a quiet period are reported at once.
- **Cross-context handoff**: queue operations are engine-thread only and unlocked. IO workers hand their entries to the PAL's cross-context enqueue (§0.2, `pal_handoff_push`), a bounded handoff that drops its oldest entry when full; the engine loop moves its entries into this queue on the engine thread (`work_queue_push_entry`), in push order (§3.2.1). Timers fire on the engine thread (item 7) and push directly.

Drain loop decisions (plan task 6, `src/graphs/runtime.h`):
- **Step budget**: one drain call handles at most a given number of entries (entries pushed during the call included) and returns; the engine loop drains again on its next iteration. So item 2's "until the queue is empty" holds across loop iterations, and a feedback cycle (item 4) cannot stop the loop from servicing sockets and timers (§3.2.1). The engine loop's budget (decided, plan task 12) is `LOOP_DRAIN_BUDGET`, 256 entries per iteration (a per-build override): a quarter of the default queue, so a busy queue still lets the loop poll its sockets every few hundred block steps, and while work remains the loop polls with timeout 0 (§3.2.1).
- **Dispatch**: an input update whose block handle or source generation is stale is discarded; otherwise it runs the block's `update`. A timer expiry whose block handle or timer generation is stale is discarded; otherwise it runs the block's compute step with `reason = TIMER` (`03-block-types.md` §2). IO events are dispatched from plan task 22; until then nothing produces them and they are discarded.

Timer decisions (plan task 8, `src/graphs/deadlines.h`, `src/graphs/runtime.h`):
- **Deadline heap**: a binary min-heap of deadlines embedded in their blocks; equal deadlines fire in arming order, so firing is deterministic. Room for one deadline is reserved when a block of a timer type is created (the heap array grows by doubling), so arming never allocates or fails while values propagate (§2.2 "Memory").
- **Firing**: `runtime_fire_timers(now)` sets the engine time, removes every deadline that is due (`<= now`), earliest first, and queues one timer expiry per block carrying the block's timer generation. `runtime_timer_timeout_ms(now)` is the time until the earliest deadline (0 if one is overdue, "none" if no timer is armed), the engine loop's poll timeout (plan task 12).
- **Generations**: arming or cancelling a block's timer (start, stop, destroy, a scheduled re-arm, a new period) increments its timer generation, so a queued expiry of a superseded or cancelled timer is discarded. A periodic timer's own continuation keeps it: its queued expiry stays valid.
- **Periodic** (`TIMER_PERIODIC`): `start()` arms the first tick one period after the start. When it fires, the timer is re-armed at once, drift-free: the next deadline is the previous one plus the period, not now plus the period. If the loop fell behind by a period or more, the missed ticks are **skipped**, not run in a burst: the next deadline is the first one of the same grid after now, and a block gets at most one expiry per firing. A cyclic block such as PID samples at a fixed rate, and several samples at the same instant would carry no information. A period of 0 arms no timer. The period is the type's `period_ms`, overridable per block instance (`block_set_period`), which restarts the timer from now with the new period; how a type's input drives it (PID's `sample_ms`, `03-block-types.md` §6.1) is decided with PID.
- **Scheduled** (`TIMER_SCHEDULED`): a one-shot timer, removed when it fires. Every compute of a started block — `START`, `INPUT` or `TIMER` — re-arms it from the return value relative to the current engine time (saturating), or cancels it if negative, so a compute for any reason supersedes a queued expiry. `STOP`'s return value is ignored: a stopped block has no timer.
- **Queue overflow**: an expiry dropped on overflow (item 9) would leave a scheduled timer disarmed for good, so if it is still the block's current expiry, the timer is re-armed to fire 1 ms later: overload delays it but never loses it. A periodic timer was re-armed when it fired and only loses that one tick, like a skipped tick.

### 3.2.1 Running this on each PAL target

The loop shape is identical on both build trees; only the primitives backing it differ:
- **Zephyr build**: one Zephyr thread (or the system work queue). The global queue can be a `k_fifo`/`k_msgq`, or — since everything runs on one thread with no cross-thread contention to guard against — a plain ring buffer is equally valid and simpler. There are no kernel timers (`k_timer`): socket I/O is polled via `zsock_poll`, whose timeout is the time until the earliest core deadline (§3.2 item 7). The hardware-module-polling worker (`04-drivers.md` §1) runs as its own Zephyr worker and must only *enqueue* readings for the engine thread — never call block logic directly from that context.
- **POSIX build**: the identical loop shape using `poll()` with the same timeout instead of Zephyr's primitives (no `timerfd`) — one thread, one queue.

Either way: `poll for I/O readiness, at most until the next deadline → fire the due timers → drain readable sockets into protocol dispatch → drain the update queue → repeat`. Write this loop once against the PAL's abstract primitives (§0) rather than duplicating it per platform.

Implementation decisions (plan task 12, `src/engine/loop.h`): the loop is portable core code over the PAL of §0.2. One iteration, in the order above, with the steps this order leaves implicit placed where they belong:
1. **Poll** the listeners and connections. The timeout is 0 if work is queued or a stop is requested; otherwise the earliest of the next block timer (`runtime_timer_timeout_ms`), every tick hook's next deadline, a connection's close linger or a listener's accept pause (below), and `LOOP_MAX_WAIT_MS` (1000 ms), so the iteration's housekeeping (drop warnings, tick hooks) runs at least once a second even when idle.
2. **Clock and timers**: one reading of `pal_uptime_ms()` is the iteration's engine time; `runtime_fire_timers` sets it on the runtime and queues the due expiries.
3. **Handoff**: the entries handed over from other contexts (§0.2) are moved into the work queue, in push order. (Placed here, beside the timers, because both are work arriving from outside the queue; an entry waits in the queue in either case.)
4. **Tick hooks**: the generic hook for other deadlines (item 7: the login nonce, session expiry; the web server's timeouts, `05-app-lifecycle-persistence.md` §3; the WebSocket handshake, liveness and close deadlines, `02-wire-protocol.md` §0; up to `LOOP_TICKS_MAX` = 8, raised from 4 in plan task 14, added with `loop_add_tick` and removed with `loop_remove_tick`). A hook is called once per iteration with the engine time, does whatever is due and returns the time until it next needs to run, which bounds the next poll.
5. **Sockets**: readable listeners accept their pending connections (at most 16 per iteration each); readable connections get their handler's `on_readable` (the protocol dispatch, which may queue work); a socket error or hang-up closes the connection.
6. **Drain** the work queue within the budget (§3.2, drain decisions).
7. **Write out** every connection's outgoing buffer as far as its socket takes it (so what steps 4–6 wrote goes out without another poll round; the rest waits for writability), close the connections marked for closing, and report queue and handoff drops (rate-limited warnings).

The loop runs until `loop_stop` (engine thread) or `pal_request_stop` (any context, POSIX `SIGINT`/`SIGTERM`); it then writes out what it can of each connection's buffer without waiting, closes every connection and listener, and returns.

Sockets are pluggable, so the HTTP server and the WebSocket layer (`05-app-lifecycle-persistence.md` §3, `02-wire-protocol.md` §0) are written against the loop, not the PAL:
- A **listener** (`loop_listen`: host, port, outgoing buffer size, an optional hard connection cap, an optional `on_closed` called when the listener is closed, also by the loop's shutdown) calls its `on_accept` for each new connection, which sets the connection's handler: `on_readable`, `on_drained` (the outgoing buffer, after holding data, has been written out — room to stream a file), `on_closed` (once, with the reason). The loop counts each listener's connections; a protocol limit that answers the client (`max_connections`' HTTP 503) is the handler's, while the hard cap closes a connection beyond it unseen, bounding resources.
- A **connection** has a bounded outgoing buffer, allocated when it is accepted (`loop_conn_set_out_cap` resizes it, keeping its contents: the WebSocket server accepts with a small buffer and enlarges it on the upgrade, `02-wire-protocol.md` §0). Writing (`loop_conn_write`) only appends to it (§4: notification writes to the connection's buffer, the loop flushes it). **A write that does not fit closes the connection** (reason "outgoing buffer full") and discards its buffered output: a client too slow to take the event stream must not silently miss events, since events are the only way its view stays in sync (`02-wire-protocol.md` §1.1); after reconnecting it starts from a fresh snapshot.
- **Nothing closes a connection from inside a call**: a close request, a failed read or a full buffer only marks it, and the loop closes it (calling `on_closed`) at the end of the iteration. Callbacks may therefore write to and close any connection at any time, including while graph events are delivered (§4). A graceful close (`loop_conn_close`) waits for the outgoing buffer to be written out, at most `LOOP_CLOSE_LINGER_MS` (5 s), so a peer that stopped reading cannot hold it open.
- A listener whose accept fails for lack of descriptors is not polled for `LOOP_ACCEPT_RETRY_MS` (100 ms), so a pending connection that cannot be accepted does not spin the loop.

### 3.3 Change threshold — only changes propagate

An output is pushed downstream only when its value has **changed** since it was last propagated:
- **Numbers** (`i64`, `f64`, `Metric` magnitude): changed when `|new − last_propagated| >= threshold`. Comparing against `last_propagated` (not the previous computed value) means slow drift still propagates once it accumulates past the threshold. A transition into or out of NaN counts as a change; NaN → NaN does not. A change of `Metric` category/unit always counts as a change.
- **Booleans, strings, unset, and any change of value type** (e.g. number → string): changed on any difference.
- The very first value after `start` is always propagated (§2.2).

The threshold is resolved in this order, first match wins:
1. the **block instance's** override (`change_threshold` in the node's metadata — `05-app-lifecycle-persistence.md` §2, settable via `graph:addnode`/`graph:changenode`, `02-wire-protocol.md` §3.4);
2. the **block type's** default (`BlockTypeDef.change_threshold`);
3. the **engine-wide** default from the configuration file (`change_threshold`, initial default `0.05` — `05-app-lifecycle-persistence.md` §1).

A threshold of `0` propagates every distinct value. The threshold is absolute; whether relative thresholds or per-output overrides are needed is open (`00-README.md`, open question 7).

An inner block of a composite instance (`03-block-types.md` §5) has no metadata of its own: step 1 is the override of the nearest enclosing composite instance that has one (in practice the instance in the graph, since the authoring format has no inner metadata), then its own type's default, then the engine-wide default (decided, plan task 21). The composite type itself has no type default (`NAN`), so an instance without an override leaves each inner block its own type's default.

Decisions (plan task 6):
- **Equal values never propagate**, whatever the threshold: a number changes when it is not equal to `last_propagated` (so `0` and `-0` are equal) **and** `|new − last_propagated| >= threshold`; at exactly the threshold it propagates. An `i64` distance is computed without overflow. Infinities follow IEEE-754 (`+Infinity` to `+Infinity` is no change).
- **"Any change of value type"** is any change of the `Linkable` tag, including `i64` ↔ `f64` and a plain number ↔ `Metric`, even when the magnitudes are equal. Strings compare by content; unset → unset is no change.
- **Valid thresholds** are `>= 0`, `+Infinity` included (numbers then propagate only on start, a NaN transition or a type change). NaN or a negative value is refused, both for the engine-wide setting and for an instance override; an instance override of NaN internally means "none".
- **"The very first value after `start`"** is the unconditional push of `start` (§2.2): a block computes and propagates only while started, so `start` always produces the first value.
- A changed threshold applies from the next `output_set`; nothing is re-propagated.

### 3.4 Time

All engine timing uses a monotonic millisecond clock starting at boot (engine **uptime**), obtained from the PAL. The wall clock is provided by the environment through its interface (`04-drivers.md` §1; `00-README.md`, open question 11). Until it is implemented, timestamps on the wire are derived from uptime (`02-wire-protocol.md` §3.3). Once a wall clock exists, it is always **UTC** — there is no time-zone handling anywhere in the system.

### 3.5 Futures collapse to direct calls

Anything that looks like it needs an asynchronous result (resolving a block type by name, building a graph's description) is, in a single-threaded engine, a plain synchronous function call with a return value — `block_types_get(name)` returns a `BlockTypeDef*` directly; `graph_describe()` builds and returns a JSON value directly. The only place genuine asynchrony belongs is I/O that must go through the event loop (socket reads/writes, timers, file access) — never a future/promise abstraction layered over otherwise-synchronous engine logic. In particular, graph loading creates each block and moves on without needing to poll for the block's existence — a block simply exists once `create_block` returns.

## 4. Event subscription / broadcast model

A `GraphNotify`-style callback interface is what `Graphs` fans every structural/lifecycle event out to: added/removed/renamed/changed block; added/removed connection; added/removed/renamed in/outport; added/removed initial; graph created/deleted/started/stopped/status; generic error. Each subscribed connection registers one such callback set (optionally scoped to a single graph once a client has issued `graph:connect` — `02-wire-protocol.md` §4.1), which turns each callback directly into an outgoing wire message. These events are the **only** way any client — including the one whose command caused the change — learns about a change to the model (`02-wire-protocol.md` §1.1). Each event must therefore describe the state actually applied, and be emitted after the mutation is complete. This is naturally a list of `(connection, optional_graph_filter)` registrations that the graph-mutation functions iterate and notify synchronously — notification is just "write JSON to this connection's outgoing buffer," which the event loop then flushes; no asynchrony is needed here. A connection whose bounded buffer cannot take an event is closed rather than left with a gap in its event stream (decided, plan task 12, §3.2.1). The WebSocket connection's buffer is `WS_OUT_CAP` (64 KiB by default, smaller on the MCU); its sizing against the `graph:connect` snapshot burst and its memory cost are in `02-wire-protocol.md` §0 (decided, plan task 14). Live link values (`network:data`), being lossy, never take the buffer's last quarter: it is reserved for events and replies, so a value stream cannot get a connection closed (`02-wire-protocol.md` §4.2 "Reserve").

Decisions (plan task 7, `src/graphs/graphs.h`): the callback set is one callback taking a tagged event struct (`GraphEvent`) plus a context pointer; the subscriber record is embedded in its owner (the connection), so subscribing allocates nothing. Subscribers are notified in subscription order. A callback may subscribe, unsubscribe (itself or any other subscriber) and re-scope, but must not change a graph: a subscriber removed during a notification receives nothing more, one added during it does not receive the event being delivered, and a re-scope applies from the next delivery. Withholding events from connections that are not authenticated (`02-wire-protocol.md` §2.5 item 6) is the protocol layer's job, not the registry's.

**Source layout and build**: each module above lives under `src/<module>/`; each PAL implementation lives under `src/platform/<port>/` (`src/platform/posix/` now, `src/platform/zephyr/` later). The repository is a plain CMake project with no RTOS dependency: it builds the portable core as a library (`hakkas_core`), the POSIX runtime, and the unit tests, all on a desktop host. Zephyr is integrated later as a separate layer (e.g. a Zephyr module) that compiles the same portable-core source list under Zephyr's toolchain, adding only `src/platform/zephyr/`. The code is C17.

Recommended C-level building blocks (libraries to consider, not a final decision):
- **Event loop / scheduling**: `zsock_poll` on the Zephyr build, `poll()` on the POSIX build, each with the time until the next core deadline as its timeout (§3.2 item 7, decided in plan task 8: no `k_timer`/`timerfd`).
- **Networking transport**: Zephyr's native BSD-sockets-style API (`zephyr/net/socket.h`) on the Zephyr build, since the device hosts the full WebSocket/FBP server and serves the frontend's static assets. For WebSocket framing/handshake: Zephyr has a minimal WebSocket implementation in its networking subsystem (`zephyr/net/websocket.h`) — evaluate whether it's sufficient or needs a thin RFC6455 layer written against the PAL (so the same framing code runs on both build trees). Avoid Linux-only libraries like `libwebsockets` if sharing this code across both PALs matters.
- **JSON** — *decided*: `cJSON`, vendored as a pinned release in `third_party/` (no network fetch at build time); it runs on both build trees. Implementation decisions (plan task 9; details, checksums and the update procedure in `third_party/cjson/README.md`): pinned to release v1.7.19, compiled into the core from `HAKKAS_THIRD_PARTY_SOURCES` (`cmake/HakkasSources.cmake`) under the core's own warning flags; `CJSON_NESTING_LIMIT` is 32 (upstream: 1000), bounding the parser's recursion on MCU stacks — a deeper document fails to parse; no custom allocation hooks — cJSON uses `malloc`/`free`, the core's heap (§2.2 implementation decisions, "Memory"), and its allocation failures are handled like any other; cJSON parses numbers exactly but does not print every double so that it reads back exactly (`0.1 + 0.2` prints as `0.3`), so an f64 that must round-trip is printed with `linkable_stringify`'s f64 form and inserted as a raw value. Decided in plan task 10 (`src/graphs/graph_json.h`): every JSON tree the core writes (graph files; the wire protocol from plan task 18) is printed through one function that first turns each number into that raw text; a number that overflowed to ±Infinity when parsed (`1e999`, the only way JSON expresses it) is printed as `1e999`/`-1e999`, which parses back to the same value. These JSON forms of the model (node metadata, the `changenode` merge, edge metadata, initial values) live in `graphs/` because the protocol layer shares them; `app/` uses them for graph files.
- **Cryptography** (SHA-256, HMAC-SHA256, PBKDF2, base64 for `02-wire-protocol.md` §2; SHA-1 and base64 for the WebSocket handshake, RFC 6455 §4.2.2) — *decided*: mbedTLS, which Zephyr already integrates and which the optional TLS support needs anyway. No hand-written cryptographic primitives. Implementation decisions (plan task 15; details, checksums and the update procedure in `third_party/mbedtls/README.md`): mbedTLS reaches the build as a **vendored, pinned copy of mbedTLS 3.6 LTS** (release 3.6.7; the same major version as Zephyr's mbedTLS 3.6 module) — not the system package, not a submodule — of which only the modules hakkas needs are copied and compiled (`sha1`, `sha256`, `md`, `pkcs5`, `base64`, `constant_time`, `platform_util`, with the headers they include), from `HAKKAS_THIRD_PARTY_SOURCES` like cJSON. It is configured by hakkas' own header, `third_party/mbedtls-config/hakkas_mbedtls_config.h` (`MBEDTLS_CONFIG_FILE`), which enables only SHA-1, SHA-256, MD (HMAC), PKCS#5 (PBKDF2) and base64: no TLS, no X.509, no PSA crypto (3.6 does not need it for these), no entropy or DRBG — random bytes come from the PAL (§0.1). The rest of the code reaches it only through `src/system/crypto.h` (SHA-1, SHA-256, HMAC-SHA256, PBKDF2-HMAC-SHA256, a constant-time compare, zeroizing, base64 and unpadded base64url), never through mbedTLS's headers. The decoders are strict: only the alphabet (and, for base64, `=` padding at the end; base64url has none), no whitespace or line breaks. The Zephyr port uses either this subset or Zephyr's own mbedTLS module (e.g. when TLS is enabled) with a configuration enabling at least the same options, never both. This replaces the temporary base64 encoder of plan task 11 (`src/system/base64.h`, removed), with the same output.
- **Persistence**: Zephyr's built-in LittleFS integration on MCU targets; a plain POSIX directory tree on the other build tree — see `05-app-lifecycle-persistence.md` for the JSON schema stored either way. The `app/` loader/saver code should only call PAL storage primitives, never a filesystem API directly.
- **GPIO/I2C/hardware IO**: consumed via Zephyr's device driver subsystem (`zephyr/drivers/gpio.h`, `zephyr/drivers/i2c.h`) behind the environment interface of `04-drivers.md` §1; hardware bring-up itself is a separate effort's responsibility.
- **Development**: either build tree works for x86_64 development — the POSIX tree for the fastest edit/compile/test loop, Zephyr's `native_sim` board when Zephyr-specific behavior needs exercising.
