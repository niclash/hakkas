# 04 — Hardware IO Layer and Networking

> **Provisional.** IO events will come from the Zephyr environment. This document captures the current intent, but the IO sections (§1–§5, §7) are expected to change substantially once hakkas is actually hooked up to Zephyr. The fixed requirement is §0: **the core program must not depend on Zephyr**, so a complete development system runs on a desktop against simulated IO.

Hardware bring-up itself — devicetree authorship, board support, peripheral driver implementations — is the responsibility of a separate effort. This document specifies hakkas' side of the boundary: the interface through which the environment tells hakkas which external inputs and outputs exist (§1), and how a graph's ports get bound to them on a given deployment (§4).

## 0. The environment SPI (decided, environment SPI design, step 4)

The engine sees IO only through the **environment service provider interface**: one environment per runtime, handed to `hakkas_create` by the host (`02-wire-protocol.md` §6) — the simulator on POSIX, the firmware's implementation on Zephyr. It replaces the earlier provisional "IO-provider" channel interface (`io_enumerate`/`io_write`). Shape:

```c
typedef struct {
	const HakkasEnvDescription *(*describe)(void *ctx);   /* the description of §1 */
	int  (*start)(void *ctx, HakkasEnvSink *sink);        /* begin delivering sensor values */
	void (*stop)(void *ctx);
	void (*write)(void *ctx, int port, int index, const HakkasValue *v);  /* actuators */
	int64_t (*wall_ms)(void *ctx);                        /* UTC wall clock, §1 */
	void *ctx;
} HakkasEnvironment;
```

Rules:
1. **Threading**: `describe`, `start`, `stop`, `write` and `wall_ms` are called on the engine thread; `write` must return at once — the environment does the actual hardware access in its own context. Sensor values may be delivered from any thread through the `sink`, which feeds the cross-context handoff (`pal_handoff_push`, `01-architecture-overview.md` §0.2, §3.2; bounded, drops the oldest entry when full); the environment never touches block state.
2. **No waiting for sensor values** (decided 2026-10-13, replacing task 22's "current values first"): hakkas never waits for sensor values at startup and has no timeout for them. Once the environment has described itself and the bindings are applied, processes start at once; blocks push their outputs on `start()` from whatever their inputs hold — a sensor-bound input without a value yet holds its port's default, so the start push drives the actuators from the defaults — and real sensor values propagate as the environment delivers them. **Protecting the real world at startup** (e.g. a start-up delay before actuators are driven) is the **environment's** responsibility: on Colibri the Zephyr driver code, which also guarantees that every channel reports a value, even when its physical sensor is dead. The environment delivers values through `hakkas_env_sink_push` (any thread). **Optionally**, within `start`, on the engine thread, it may hand over values it already has through `hakkas_env_sink_current`, which the engine takes at once rather than through the handoff — they are then there before any binding is applied or process started (startup steps 5 and 7 of `05-app-lifecycle-persistence.md` §1.4), and a large environment's burst cannot overflow the handoff (useful for the Zephyr firmware, which knows its values at start). Nothing requires or waits for a value per channel. Waiting for the **description** at startup stays (bindings need it, §0.1).
3. **Actuator writes**: `write` is called whenever a bound block output propagates, including the unconditional push when its process starts. When nothing drives an actuator (process not loaded, stopped, binding absent), hakkas writes nothing and the output keeps its last value (`03-block-types.md` §4).
4. **Change threshold**: a sensor value is filtered by the engine-wide default change threshold like any output (`01-architecture-overview.md` §3.3); a `process/Deadband` in the graph filters it differently where needed.

Everything above the SPI — applying bindings, delivering sensor values to the bound block inputs, calling `write` for bound outputs — is platform-independent (`drivers/`, `01-architecture-overview.md` §6).

**Implementation decisions** (plan task 22; the public header `src/hakkas_env.h`, included by `src/hakkas.h`; the engine's side `src/drivers/environment.h`):
- **C types**: `HakkasValue` is the core's value (`01-architecture-overview.md` §2.1). `HakkasEnvDescription` is §1's description: `name`, `description`, `icon`, `in_ports`/`out_ports` (arrays of `HakkasEnvPort`: `id`, `type` `HAKKAS_ENV_NUMBER`/`_BOOL`, `description`, `unit`, optional `min`/`max`, `addressable`, `count`) and `modules` (`HakkasEnvModule`: `slot`, `type`, `vendor`, `revision`, `serial`, `documentation`, and the ids of its `ports`). `HakkasEnvSink` is opaque: `hakkas_env_sink_push(sink, port, index, value)` delivers a value (any thread), `hakkas_env_sink_current(...)` optionally a value the environment already has (within `start`, rule 2); `port` indexes `out_ports`, `index` is the channel. A value is an f64, i64 or bool, converted to the port's type (`number` → f64, `bool` → bool); a push for a port or channel the description does not have, or of another type, is refused (`false`). `write` gets the value converted to the actuator port's type the same way. `start` returns 0 or an error code, which refuses startup.
- **Channels**: an addressable port's channels are `1…count`; a port that is not addressable has one channel, index `0` (a bindings file without `"index"`).
- **One environment per runtime, optional**: `HakkasParams.environment` of `hakkas_create` (`02-wire-protocol.md` §6), `NULL` for none. **Startup step 5** (`05-app-lifecycle-persistence.md` §1.4): `describe` (which may wait for the environment, as the POSIX link does, §0.1), validation, `start`; each failure refuses startup. **Validation** of the description: a `name` of 1–64 bytes; port ids of 1–64 bytes, **unique across both directions** (a binding names the port by id alone); types `number` or `bool`; an addressable port's `count` 1–1024 (`HAKKAS_ENV_COUNT_MAX`), none for one that is not; `min ≤ max` when both are given; at most 256 ports and 64 modules; other strings at most 1024 bytes; a module may list only ports of the description. The description must stay unchanged until `stop`. `stop` is called at shutdown, after the listeners close and before the loop (and its handoff) goes; no sink call may follow it.
- **Sensor values** (rule 4): the engine converts each value to its port's type and filters it per channel by the engine-wide change threshold against the channel's last delivered value (the first one always passes), then delivers it to every block input bound to the channel through the block's update, like any value change (`01-architecture-overview.md` §3.2: an IO event of the work queue, dispatched to the bound inputs; a stopped process only stores it). The value of a channel nobody binds yet is still its current value, which a later binding delivers at once.
- **Wall clock** (§1): `wall_ms` may be `NULL`; then, and without an environment, the platform's clock (`pal_wall_ms`, `01-architecture-overview.md` §0.1) is the fallback.

### 0.1 Implementations of the SPI (decided, environment SPI design, step 5)

- **Zephyr**: the device firmware implements the SPI in C directly (the Colibri environment, §1).
- **POSIX — the external environment link**: the environment is a **separate program** (a simulator, e.g. of a Colibri system — the Colibri emulator, `emulators/colibri/specifications/`; possibly others later), developed as its own project. Hakkas' POSIX build contains only an adapter implementing the SPI by talking to it over a **Unix domain socket**:
  - **The environment program is the server**: it owns the socket, at the path given by the configuration key `environment.socket` (`05-app-lifecycle-persistence.md` §1.1); hakkas connects as a client. Without that key there is no environment, and any bindings file is refused (it can't match).
  - **Messages** are newline-delimited JSON, transport-neutral (a later WebSocket transport would change only the framing). The environment program sends its **description** (§1, including modules and their metadata) first, then sensor values — its current ones as it has them, then changes (hakkas waits for none of them, §0 rule 2); optionally the **wall clock** (allowing simulated time). Hakkas sends a version greeting, then **actuator writes**. The message set (decided, plan task 22) — one JSON object with one member per line, UTF-8, a line at most 256 KiB:
    - hakkas → environment: `{"hello": {"version": 1}}` first on every connection; `{"write": {"port": "<id>", "index": <n>, "value": <number|bool>}}` for an actuator value (`index` only for an addressable port; a NaN number is written as `null`, an infinity as `1e999`/`-1e999`).
    - environment → hakkas: `{"describe": {<the description of §1>}}` first on every connection, without waiting for the greeting; `{"value": {"port": "<id>", "index": <n>, "value": <number|bool>}}` for a sensor value (`index` absent or `null` for a port that is not addressable); `{"clock": {"wall_ms": <integer>}}` for the wall clock.
    - A line whose object has another member is ignored (forward compatibility). A line that is not a JSON object, or a message with invalid contents (an unknown or actuator port, a channel the port does not have, a value that is neither a number nor a bool, a value before the description), is logged as a warning (at most 8 per connection) and ignored. A longer line ends the connection, like a disconnect.
  - **Startup waits for the environment**: bindings need the description, so hakkas logs `waiting for environment at <path>` and retries every second until it has the description, and only then loads processes and applies bindings. (Decided, plan task 22: the wait is logged once, as a warning. Revised 2026-10-13: startup waits for the description only, **never for sensor values** and with no timeout for them, §0 rule 2; sensor values the program sends before or after processes start are delivered normally — those read together with the description are handed over by `start` through `hakkas_env_sink_current`, every later one by the link thread. A stop request — `SIGINT`/`SIGTERM` — ends the wait and `run` exits cleanly. A description that does not parse or validate refuses startup; the connection ending during startup starts the wait over.)
  - **Disconnect while running**: sensor-bound inputs keep their last values (as actuators keep theirs, `03-block-types.md` §4); hakkas logs it and reconnects automatically. On reconnect the description must be identical — bindings are applied only at startup — otherwise hakkas logs an error and resumes no IO until restarted. The environment re-sends all current sensor values, and hakkas re-sends every actuator's last value. (Decided, plan task 22: a disconnect is the end of the stream, a read or write error, or an over-long line; "identical" is equality of the parsed descriptions, member by member, ports and modules in order. The reconnect retries every second; after it hakkas re-sends the latest value of every actuator channel it has written, also those written while disconnected; the environment's re-sent sensor values pass the engine's change threshold, so only changed ones propagate. A changed description closes the connection for good: `environment at <path> changed its description: no environment IO until hakkas is restarted`.)
  - **Implementation** (decided, plan task 22; `src/platform/posix/env_link.h`): the adapter's startup (`describe`) runs on the engine thread inside `hakkas_create`; `start` hands over the sensor values read together with the description, if any (`hakkas_env_sink_current`), and starts one **link thread**, which owns the connection from then on: it reads lines and delivers sensor values through the sink, writes actuator values, and reconnects. The link thread never logs (`05-app-lifecycle-persistence.md` §4): it queues its messages and the engine thread logs them from a loop tick hook, within a second. **Actuator writes never block the engine thread**: `write` stores the value as the channel's latest and marks the channel pending, in a FIFO of pending channels with at most one entry per channel (bounded by the description); the link thread sends pending channels in the order they became pending, each with its latest value. **Overflow policy**: nothing is dropped — when the environment reads slower than hakkas writes, a channel's successive values coalesce into its latest, which is always sent. The **wall clock** is the last `clock` received, advanced by the engine's monotonic clock since it arrived (simulated time runs on between messages); before any, the host's clock (`pal_wall_ms`). At shutdown the link thread writes out what it can of the pending values without waiting, then ends. The socket path must fit a Unix socket address (107 bytes on Linux), else startup is refused.

## 1. The environment and its interface (decided, open question 2)

There is no EEPROM and no module discovery by hakkas. The hardware platform these sections originally described no longer exists; hakkas does not read module descriptors, probe expansion slots, or drive registers itself.

Instead, the **environment** — whatever hosts hakkas and owns the physical inputs and outputs (the device firmware on Zephyr, a simulator on POSIX) — provides a **service provider interface** that hakkas queries for the external inputs and outputs that are available. The environment describes them in the same terms as block types (`01-architecture-overview.md` §2.3, `02-wire-protocol.md` §3.5): named, typed, described ports, with an icon and a description. The one principal difference from a block type is that an environment **cannot be instantiated**: it exists once, whether or not a graph uses it, and the user cannot create or delete it. On the wire, the environment's description, bindings and everything else about the environment go in the **`environment` protocol group** (decided 2026-10-24), each message put to the user first. Presenting it nicely in the user interface needs dedicated handling there. **Deferred to the frontend work** (environment SPI design, step 6): until then the environment is not visible on the wire at all — bindings come only from bindings files, and the user interface sees the bound block ports as ordinary ports.

**Description model** (decided, environment SPI design, step 1): the environment describes itself with the shape of a component descriptor (`02-wire-protocol.md` §3.5) — `name`, `description`, `icon`, `inPorts`, `outPorts` — seen **from the graph's side, as one block that cannot be instantiated**:
- its **output ports** are the plant's inputs to hakkas (sensors, digital inputs, meters): values that flow *into* graphs;
- its **input ports** are hakkas' outputs to the plant (relays, analog outputs): values graphs *send out*.
Each port has `id`, `type` (`number` or `bool`), `description`, and optionally `unit` and `min`/`max` (descriptive, for the user interface only — values are plain numbers, `01-architecture-overview.md` §2.1). A port that stands for a group of identical channels is **addressable** (`"addressable": true`) with a `count`: its channels are indexed `1…count`, as in the sister project's bindings (`{"port": "analog-in", "index": 1}`). Example:
```json
{"name": "emulator", "description": "Desktop simulator", "icon": "chip",
 "outPorts": [{"id": "analog-in",  "type": "number", "addressable": true, "count": 8, "unit": "V", "description": "0-10 V inputs"},
              {"id": "digital-in", "type": "bool",   "addressable": true, "count": 16}],
 "inPorts":  [{"id": "analog-out", "type": "number", "addressable": true, "count": 4, "unit": "V"},
              {"id": "relay",      "type": "bool",   "addressable": true, "count": 8}]}
```
User-facing naming from the plant's point of view (e.g. calling a sensor an "input") is a presentation matter for the user interface, e.g. via metadata; it does not change this model.

**Modules and their metadata** (decided): an environment may be modular. Its description then also lists its **modules**, each with descriptive metadata that the user interface shows — e.g. slot, module type/model, vendor, hardware revision, serial number, documentation link — and the ports each module contributes. Like all metadata this is for the user interface only (`01-architecture-overview.md` §2.2); bindings refer to ports and channel indices, never to serial numbers.

**The carrier board** (decided with the user 2026-10-24; *not implemented yet* — `HakkasEnvDescription` and the link's `describe` have no carrier; the shape below is a proposal): a modular environment's description also describes its **carrier board**:
- its type, vendor, revision, serial number and documentation, like a module's;
- the **number of I/O slots**;
- its **built-in slot(s)**: a list, each entry with its slot number; each holds an **I/O module that cannot be changed**, listed among the modules like any other (marked `builtin`), with its ports. (Whether a carrier will ever have more than one — a fixed I/O module to lower the price — is not known; the list allows it.)
- its **power specification**: the supply voltage range, AC and/or DC, the supply current;
- its **communication slot(s)**: per slot the communication module's type and its **parameters, which differ per type** — **view only** (decided 2026-10-24: the description shows what the device runs; configuring them this way may be revisited):
  - **Ethernet** and **WiFi**: DHCP or a static address — `mode` (`dhcp`/`static`), `address`, `prefix`, `gateway`, `dns` (a list), and the `mac`; with DHCP the addresses are those currently leased. WiFi also its `ssid`. Addresses are IPv4 or IPv6 strings.
  - **RS-485**: `bitrate` and `parity` (`none`/`even`/`odd`).
  - **LoRaWAN**: OTAA deployments only; `appEui` and `devEui` (16 hex digits each), and `appKeySet` (bool) — the App Key is a secret, so only whether one is set is shown, never the key (decided 2026-10-24).
  No secret (a WiFi passphrase) is ever part of the description (`02-wire-protocol.md` §2).
```json
{"name": "colibri", "carrier": {"type": "colibri/Colibri8", "vendor": "CurrentMakers", "revision": "B", "serial": "…",
   "slots": 7,
   "power": {"voltage": {"min": 12, "max": 30}, "ac": false, "dc": true, "current": 2.0},
   "comm": [{"slot": 1, "type": "colibri/Ethernet",
             "ip": {"mode": "dhcp", "address": "192.168.1.40", "prefix": 24, "gateway": "192.168.1.1",
                    "dns": ["192.168.1.1"], "mac": "02:00:00:00:00:01"}}]},
 "modules": [{"slot": 0, "type": "…", "builtin": true, "ports": […]}, …], …}
```
Like all metadata it is for the user interface only, and it is what the Colibri emulator copies from a device (`emulators/colibri/specifications/00-README.md` §5.3).

**The Colibri environment** (the target hardware, https://stm32world.com/wiki/Colibri; the wiki is partly out of date): a carrier board (Colibri 8: 7 I/O slots plus one I/O slot built into the carrier board, so that the firmware treats the board's own I/O like a module's; a Comm slot with the W5500 Ethernet; an MCU slot — RP2354 or STM32H562) holding I/O modules that the firmware identifies at boot from each module's EEPROM, whose position-independent driver code the firmware runs cyclically. All of that is the firmware's side of the SPI; hakkas reads no EEPROM (`00-README.md` open question 2). Decided for its description:
- **Ports are named per slot** (e.g. `slot3-ai` for the analog inputs of an AIV module in slot 3, `slot5-dq` for an SSR in slot 5; channel groups are `ai` analog input, `aq` analog output, `di` digital input, `dq` digital output, whatever the hardware — decided 2026-10-23), so a binding names a physical terminal; moving a module to another slot changes the bindings, as it changes the field wiring. Each slot's module appears in the description's module list with its type, serial number and other metadata.
- **Scalar modules map directly**: analog inputs (AIV 0–10 V, AIC 0–20 mA), temperatures (Pt100/Pt1000), pressures (DP1–DP3) and digital inputs (DII/DIU: per channel frequency, duty cycle and a 32-bit unsigned counter that rolls over) are sensors; analog outputs (AQV), digital outputs (FET), relays (SSR, Fallback) and triacs (TRIAC1) are actuators.
- **DIO1**: each channel is **both** a sensor and an actuator port (a binding uses one of them per channel); on the actuator side the module detects hardware faults, which appear as additional **sensor** ports (fault flags) of the module.
- **PID1** (a full PID regulator on the module) is sensors and actuators like any other: its Pt1000 measurement and its output are sensors; every PID parameter (setpoint, P/I/D, limits, manual mode and value, …) is an actuator.
- **RS-485 modules** (RS485I, RS485U; Modbus etc.) are not defined yet and outside hakkas' scope; they are not described to hakkas.
- **Lua user programs**: Colibri firmware runs user Lua scripts today. Hakkas competes with them — the aim is that hakkas replaces them, or complements them where dataflow is the more natural abstraction. While both exist on one device, the firmware decides which channels hakkas is offered (e.g. a channel driven by a Lua script is not offered as an actuator), so the one-driver rule of §4 holds across both.

The environment interface also provides the **wall clock** (`00-README.md`, open question 11): calendar blocks (`03-block-types.md` §6.2) and wire timestamps read real time from it; on POSIX the simulated environment uses the host's clock.

**Implemented** (plan task 22, replacing plan task 24's interim): the wall clock is the environment's `wall_ms` (§0). Without an environment, or when it gives no `wall_ms`, the platform's clock `pal_wall_ms()` (UTC ms since the Unix epoch; POSIX `CLOCK_REALTIME`, `01-architecture-overview.md` §0.1) is the fallback. The engine loop, the startup and the local C API read it into the runtime, which takes it as an injected value with the step handling of `01-architecture-overview.md` §3.4; wire timestamps are built from it (`02-wire-protocol.md` §3.3). The POSIX external environment link gives the environment program's `clock` messages, else the host's clock (§0.1).

How a graph's ports are connected to the environment's ports — so that the same graph runs unchanged in different environments, by applying a different bindings file — is open question 3 (§4). How the environment appears in the graph model and on the wire is open question 6.

On the Zephyr build the environment's implementation (device drivers, devicetree, board support) belongs to the device firmware, not to hakkas; on POSIX it is the simulated provider (§0).

## 4. Discovery and binding

1. At boot, hakkas queries the environment (§1) for its available inputs and outputs.
2. *(Removed with the EEPROM, open question 2.)*
3. **Binding** (platform-independent, above the environment SPI): an ordinary block port (`"<block>.<port>"`) is associated with one environment channel; there are no `io/*` blocks (`03-block-types.md` §4). **A binding is a connection** between the environment block (§1) and an ordinary block (decided, environment SPI design, step 2), with the connection rules of `01-architecture-overview.md` §2.2:
   - a **sensor** — a channel of an environment *output* port — binds to a **block input**, and becomes that input's one source (no fan-in: the input can have no connection, initial or link besides it). One sensor channel may feed any number of block inputs, in any number of processes;
   - an **actuator** — a channel of an environment *input* port — binds to a **block output**. One block output may drive several actuators, but each actuator channel has exactly **one driver across the whole deployment**; a second binding to the same actuator channel is refused when the bindings are applied.
   There is no "tap" binding of an actuator to a block input. The sister project's `examples/bindings-emulator.json` predates this design and is not authoritative (it binds an actuator to a block input).
4. **Portability**: the same graph must run against different physical hardware configurations. The binding from a graph's logical IO reference to an actual discovered slot/channel is resolved per-deployment, at boot — not baked into the portable graph file. The graph itself contains no reference to hardware; a separate binding configuration maps its block ports to this environment's ports. The binding configuration is a **bindings file** per process and environment, paired with its process in the process list (`"bindings"` member, `05-app-lifecycle-persistence.md` §1.2). **Format** (decided, environment SPI design, step 3):
   ```json
   {"environment": "emulator",
    "bindings": [
      {"block": "block1", "port": "in1", "env": "analog-in",  "index": 1},
      {"block": "block7", "port": "out", "env": "analog-out", "index": 1}
    ]}
   ```
   - `environment` names the environment the file was written for. **It is information, not enforcement** (decided 2026-10-24, replacing the refusal of plan task 22; *not implemented yet* — the code still refuses): if it differs from the running environment's `name`, hakkas logs a warning and applies the file. Naming is not relied on to keep emulator bindings off real hardware; the user chooses the bindings file when deploying a process, and mismatching entries are shown to be mapped then (`06-frontend.md` §7).
   - Each binding names a block port (`block`, `port`) and an environment port (`env`); `index` (1…`count`) is required for an addressable environment port and absent otherwise. The direction is not written: an environment output port is a sensor and must bind a block input, an environment input port is an actuator and must bind a block output.
   - **Warn and skip, never refuse** (decided with the user 2026-10-24, replacing plan task 22's refusals; *not implemented yet*): an entry that cannot be applied — an unknown block or port, the wrong direction, an input that already has a source, a second driver for an actuator channel — is **skipped with a warning**, and the file's other entries are applied; bindings never refuse startup. The rules that make an entry inapplicable stay (no fan-in, one driver per actuator channel, `01-architecture-overview.md` §2.2): a skipped entry is simply not made. A malformed file (not the form below) is not applied at all, with a warning, and its process loads and starts without bindings. In the frontend, **any warning brings up the mapping dialog** (`06-frontend.md` §7), so the user resolves what was skipped.
   - **A channel the environment doesn't provide is not an error** (item 6): an unknown environment port or an `index` beyond its `count` is skipped with a warning, and the block port stays inert — so one bindings file also works on a board variant with fewer channels.
   - **Implementation decisions** (plan task 22; `src/drivers/bindings_file.h`, `src/drivers/environment.h`, the model in `src/graphs/graph.h` "Environment bindings"):
     - **The file's form**: one JSON object with a non-empty string `environment` and an array `bindings` (empty allowed) of objects with non-empty strings `block`, `port`, `env` and an optional integer `index` ≥ 1 (`null` is absent); a member the format does not know is logged as a warning and ignored, like the process list's; anything else is a malformed file (until 2026-10-24 refusing startup; now a warning, above). The file is at most 64 KiB (`HAKKAS_BINDINGS_FILE_MAX`).
     - **Applying a file was all or nothing** (plan task 22; revised 2026-10-24 to warn and skip per entry, above — the messages below then become warnings `<file>: bindings[<i>]: <message>: skipped`): every entry is checked first — in file order, against the bindings already made and the file's earlier entries (an input bound twice, an actuator channel driven twice) — and only if none is refused are they made, in file order. The refusals (C API messages, `02-wire-protocol.md` §6), as `bindings[<i>]: <message>`: `Invalid id`, `Index required: <env>` (an addressable environment port without `index`), `No index expected: <env>`, `Unknown node: <block>`, `Unknown port: <block>.<port>`, `Invalid binding direction`, `Input already connected: <block>.<port>`, `Actuator already driven: <env>[<index>]` (or `<env>`); before them `No environment`. (`Environment mismatch: <the file's> (running: <name>)` becomes a warning, decided 2026-10-24, above.) The skips are warnings `<file>: bindings[<i>]: Unknown environment port: <env>: skipped` and `… Index out of range: <env>[<index>]: skipped`.
     - **A sensor binding is a source kind** of the bound input, beside a connection, an initial and a link (`01-architecture-overview.md` §2.2): with its own source generation and no fan-in either way — a sensor onto an input with any source (a retained connection included) and a connection, initial or link onto a sensor-bound input are refused with `Input already connected`. One sensor channel may feed any number of inputs. A composite instance's input or output may be bound (its mapped inner port carries the values, as for a link).
     - **Making a binding** reports `BINDING_ADDED`, then delivers what is there: a sensor binding the channel's current value (if the environment has delivered one), through the input's update; an actuator binding on a started process writes its output's current value at once. A binding made before its process starts writes at the start push.
     - **Ending a binding** (decided): removing it (the C API, `hakkas_binding_remove`) reports `BINDING_REMOVED`, and a **sensor-bound input then reverts to its port default**, which propagates — exactly like any severed input (`01-architecture-overview.md` §2.2); values of the channel queued but not yet delivered reach only the inputs still bound. Removing the bound block removes its bindings with its connections (its inputs' in port order among its edges and initials, its outputs' after its outgoing edges, before its graph ports); deleting the process removes them after its stop and before its deletion is reported. An **actuator keeps its last value** whenever its binding ends (`03-block-types.md` §4): nothing is written. Renaming the block keeps its bindings. At shutdown bindings go without events.
     - **Events**: `BINDING_ADDED`/`BINDING_REMOVED`, graph-specific, in applied order; the C API delivers them, and they have **no wire message** (the environment is not on the wire yet, §1; `02-wire-protocol.md` §6).
5. An environment output port (sensor) delivers its values to its bound block inputs, which propagates the value exactly like any other value change (`01-architecture-overview.md` §3); an environment input port (actuator) receives each new value of its bound block output through the SPI's `write` (§0). An output keeps its last value whenever nothing drives it (`03-block-types.md` §4).
6. **Graceful degradation**: a logical IO reference with no live binding on a given deployment (the environment doesn't provide that input or output) holds its default value and takes no other action — it doesn't fail graph startup. This is what makes a graph portable across differently-configured hardware: references to IO points a particular board doesn't have simply stay inert.

## 5. What hakkas owns vs. the separate hardware effort

Hakkas owns: the environment interface it queries (§1, §0), the simulated environment on POSIX, the FBP-facing behavior of whatever represents the environment in graphs (open question 6), and the binding of graph ports to environment ports (§4) including graceful degradation.

The environment's side — on Zephyr the device firmware: devicetree, board support, device drivers, and the implementation of the environment interface — belongs to the separate hardware/firmware effort. There is no EEPROM descriptor format.

## 6. Networking on the Zephyr targets — proposal

Nothing here has been worked on yet; this is a proposal to start from. The device hosts the full WebSocket/FBP server and serves the frontend's static assets, on Zephyr's native IP stack and BSD-style socket API (`zephyr/net/socket.h`), never a Linux-specific library. See `01-architecture-overview.md` §6 for the module/library guidance and the PAL split that keeps this isolated from the POSIX build tree.

**Network interface hardware** — this is the first decision, and it needs the hardware effort:
- **STM32H5/H7/N6**: on-chip Ethernet MAC + external RMII PHY, supported by Zephyr's STM32 Ethernet driver. This is the most straightforward path.
- **RP2354 (RP2350)**: has no on-chip network interface. Options:
  - a **WIZnet W5500** SPI Ethernet controller, which has a Zephyr driver (`wiznet,w5500`) and runs Zephyr's own IP stack. **Recommended** for a wired controller.
  - an **Infineon CYW43439** Wi-Fi chip, as on the Pico 2 W. Verify Zephyr's driver support for it on the RP2350 before committing.
  - ENC28J60 (10 Mbit, also supported by Zephyr) as a low-cost fallback.

**IP configuration**:
- A DHCPv4 client (`CONFIG_NET_DHCPV4`), with a static address from the configuration file as override (`05-app-lifecycle-persistence.md` §1.1).
- IPv4 link-local addressing (`CONFIG_NET_IPV4_AUTO`) as fallback, so a laptop connected directly with a cable can still reach the device.

**Discovery**: an mDNS responder plus DNS-SD (`CONFIG_MDNS_RESPONDER`, `CONFIG_DNS_SD`) advertising:
- `<hostname>.local`;
- `_http._tcp` on `port`;
- `_fbp-ws._tcp` on `port+1`, with the TXT records the upstream FBP protocol defines (`fbp-protocol.html`, "Runtime discovery": `txtvers=1`, `id=<engine_id>`, …).

The user can then type `http://<hostname>.local:<port>/` instead of an IP address.

**HTTP + WebSocket server** — two options:
1. A small, portable HTTP/1.1 `GET` server plus an RFC 6455 WebSocket layer, written once against the PAL socket primitives and used by **both** build trees. It integrates directly into the single-threaded engine loop (`01-architecture-overview.md` §3.2.1). **Recommended**: the same code runs on desktop and device, and no cross-thread handoff is needed. The HTTP server is built this way (plan task 13, `05-app-lifecycle-persistence.md` §3); its buffer sizes and connection count are per-build overrides to size for the MCU.
2. Zephyr's built-in HTTP server (`CONFIG_HTTP_SERVER`, with static/gzip resources and WebSocket upgrade support). Less code to write, but it runs on its own thread(s), so every received frame would have to be handed into the engine queue, and the POSIX build would need a different server. Keep it as a fallback if code size or schedule demands.

**TLS**: optional, via Zephyr's mbedTLS-backed TLS sockets (`02-wire-protocol.md` §2.5 item 9); off by default.

**Wall clock**: the environment provides UTC (`04-drivers.md` §1); on Zephyr, SNTP (`CONFIG_SNTP`) or an RTC is the natural source — the firmware's business. Local time for calendar blocks comes from the `time_zone` setting (`00-README.md`, open question 11).

**Sizing**: socket count and network buffer Kconfig options (`CONFIG_NET_MAX_CONN`, buffer pools, …) are sized from `max_connections` + 1 listener per port + DNS/mDNS/DHCP. Web assets are stored pre-gzipped (`05-app-lifecycle-persistence.md` §3).

## 7. Addressable expansion buses (Modbus and similar)

If the hardware lineup ever needs Modbus-connected devices or other addressable-expansion-over-a-shared-bus patterns, implement them as another binding behind the same generic-driver/binding-table model (§3–4), not as a separate bespoke subsystem. Whether this is actually needed depends on the separate hardware effort's design.
